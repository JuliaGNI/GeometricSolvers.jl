CPU and GPU backends

GeometricSolvers runs the same solvers on the CPU and on CUDA, ROCm and Metal devices. This page describes how the code is built for that: the four kinds of object, the storage seam, the reduction seam, dispatch in place of checks, and the vendor libraries that replace some of the own kernels.

Four kinds of object

objectholdsexample
problemfunctionsNonlinearProblem
methodnumbers, types and sub-methods, and no buffer of the solveNewton, LUFactorization, Backtracking
stateeverything that is allocated or that changes during a solvethe result of init_state
statusthe resultSolverStatus

A problem holds no parameters and no iterate, and a method holds no buffer of the solve. When every field of the problem is isbits (the residual, the Jacobian function and the prototype, if any), the problem and every method that runs in R1 are isbits, so a kernel takes them by value. A Matrix prototype, for example, makes the problem non-isbits, and solve_batch! rejects it. The state of an R1 solve is isbits too: every buffer slot is nothing.

KernelAbstractions backends

The device code is written once with KernelAbstractions. get_backend(x) of the iterate selects the backend: CPU() for a host Array, and the backend of CUDA, AMDGPU, Metal or any other GPU array package. The package depends on no vendor package; a vendor package loads its own backend, and the package extensions for CUDA and Metal load with it.

  • solve_batch! launches one kernel on get_backend(X) with one work-item per system.
  • The device factorisations (DeviceLU, DeviceQR, DeviceLDLT, DeviceCholesky, DeviceSVD) are sequences of KernelAbstractions kernels on an AbstractGPUArray.
  • The chunked forward mode of ForwardDiff and the reductions run on any array type, with broadcasting and sum and no scalar indexing.

The storage seam: one algorithm over two kinds of storage

R1 returns new values and R3 writes into buffers. That difference is at the leaves of an algorithm, not in its logic. Every algorithm — the loop, Newton, Picard, the line searches, DogLeg, the combinators and Anderson — is written once over a small set of functions with a !! suffix. Each has a method for a value and a method for a buffer:

update_iterate!!(::Nothing, x, α, d) = x + α * d                   # R1: a new value
update_iterate!!(y::AbstractArray, x, α, d) = (y .= x .+ α .* d)     # R3: into the buffer

An algorithm always rebinds the result, xt = update_iterate!!(state.xt, x, α, d), so it reads the same in both regimes. The seam consists of buffer, residual!!, update_iterate!!, map!!, mul!!, copy!!, scale!!, axpby!! and regularize!!, together with jacobian!!, jvp!!, factorize!! and ldiv!!. A backend or a library adds methods to these functions, and a vendor library to the back substitution backsolve! of its factor, never a new function.

The !! convention is that of BangBang.jl; the package defines its own methods and does not depend on BangBang.

The reduction seam

Every norm, dot product and merit value goes through four functions: norm2 (the squared norm), rnorm (the norm, scaled against overflow and underflow), rmaxnorm (the max norm, which the residual test reads under MaxNorm) and rdot (the real part of the inner product). Each returns R = real(eltype(x)), and none of them indexes scalars, so they run on an SVector inside a kernel, on an Array and on a GPU array. A widened or compensated accumulator would be a change in these four functions and nowhere else.

In R1 and R3 a missing method is a MethodError on the host. The value checks that a type cannot express, such as a negative tolerance, raise an ArgumentError in a constructor, on the host. Inside a kernel nothing throws: a numerical failure is a ReturnCode.

Kernel-safe types

ReturnCode is one byte, and the counters of SolverStatus, StepInfo and Options are Int32 or Int16, because 64-bit integers cost registers on a GPU. Every real field is in R = real(T), so these types bring no Float64 into a Float32 kernel; the parameters and the factorisation precision are the caller's (see Device precision). A factorisation precision is a type parameter of the method (LUFactorization{Float32}) and not a field, because a type stored in a field is not isbits. Verbosity, traces and warnings do not exist in the core; a caller reads the status.

  • On the host, LUFactorization() factorises an n × n Float32, Float64 or ComplexF64 matrix with 8 ≤ n ≤ 32 by an own recursive LU with partial pivoting: the columns split in halves down to panels of at most 16 columns, which an unblocked kernel factorises, and BLAS trsm and gemm update the rest. It picks the pivot of largest |Re| + |Im|, the first one on a tie, as LAPACK does, and writes LAPACK's ipiv, so getrs solves with its factor. The band is where scripts/hardware/rl_host_lu.jl measured the recursion at 0.90 or less of the time of getrf, with BLAS on one thread and on all threads: Apple M4 Max, OpenBLAS 0.3.30, Julia 1.13.4. Every other n, and ComplexF32, call getrf.
  • The CUDA extension GeometricSolversCUDAExt adds methods for DeviceLU, DeviceQR, DeviceSVD and DeviceCholesky on CuMatrix{T} with T <: LinearAlgebra.BlasFloat. Other element types stay on the own kernels.
  • The Metal extension GeometricSolversMetalExt adds the Metal Performance Shaders LU and triangular solve for MtlMatrix{Float32}. Every MPS failure status gives a singular factor. ComplexF32 and the other factorisations stay on the own kernels.
  • The ROCm extension GeometricSolversAMDGPUExt adds the rocSOLVER and rocBLAS methods for DeviceLU, DeviceQR and DeviceCholesky on ROCMatrix{T} with T <: LinearAlgebra.BlasFloat. rocSOLVER geqrf and ormqr and rocBLAS trsv serve every shape of the QR factor: the solve with the m × n factor of a least-squares problem, m > n, runs trsv on its leading n × n block. Other element types and the other factorisations stay on the own kernels.

A vendor method replaces only factorize!! and the back substitution of its factor type. The scaling by a power of two, the mixed-precision solve and the status handling are the same on every backend. The own Cholesky kernel is one workgroup of 64 work-items, as the LDLT kernel is; the vendor potrf methods take its load kernel first, which refuses a non-finite matrix with info = 1 before potrf and divides a matrix of another element type than the factor by its power of two.

The factor that a sparse R3 solve uses, on a sparse jacobian_prototype:

factorisationhost Vector, SparseMatrixCSCCuVector, CuSparseMatrixCSR (CUDA)other arrays
LUFactorizationSparspak for a real element type, with Sparspak loadedcuDSS for BLAS element types, with CUDSS loadedno sparse factor

  • The cuDSS extension GeometricSolversCUDSSExt, loaded with CUDA and CUDSS, adds the sparse LU of LUFactorization() on a CuSparseMatrixCSR{T} prototype and a CuVector{T} iterate, T <: LinearAlgebra.BlasFloat. The cuDSS analysis runs once, at the first factorisation, and every later factorisation is a refactorisation. Its Jacobian comes from an analytic J, because an AutoSparse back end needs a host array.

A sparse factor has its own init_linear, factorize!! and ldiv!!, and factorises in the element type of the iterate only: it takes no scaling by a power of two and no mixed precision.

R1 and R2 use the static factorisations on every backend, because they run in one thread. The sparse LU of Sparspak and that of UMFPACK run on a host Vector only. The stacked LevenbergMarquardt path, that of every factorisation other than SVD and of scaling = :diagonal, indexes scalars and runs on a host array only, and an AD back end other than AutoForwardDiff() needs a host array.

Device precision

backendFloat64Float32complex
CPUyesyesyes
CUDAyesyesyes
ROCmyesyesyes
MetalnoyesComplexF32

Metal has no Float64, so a Metal solve runs in Float32 throughout: the iterate, the residual, the tolerances, the factorisation and the status. The keywords build the Options in real(eltype(x)), and ToReal converts every float value of the method to that type. ToReal does not change a type parameter or the parameters p: a factorisation precision such as LUFactorization(Float64) and a Float64 parameter keep their types, so the caller chooses them in Float32. With T = Float32, the pair T = Float64, TF = Float32 of Mixed precision does not apply on Metal; it applies on the CPU, CUDA and ROCm.

The markers TF32, FP16 and BF16 name tensor-core precisions as a type only. No factorisation method takes a marker, so a marker selects no code path.

Device tests

The device tests run by hand on the machines that have the devices; the repository's test/gpu/README.md describes the runs. The JLArrays reference GPU array runs the device code paths on the CPU in the regular test suite, with scalar indexing disallowed.
