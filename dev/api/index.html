API

The problem

A problem holds functions and nothing else: the residual, and optionally its derivative. The storage of the iterate selects the call form of both, so one problem serves every regime. This name is exported.

GeometricSolvers.NonlinearProblem — Type
NonlinearProblem(F)
NonlinearProblem(F, J)

The residual F of a nonlinear system, and optionally its derivative J. The problem holds functions only — no parameters, no iterate and no flag — so it is isbits when F and J are and a kernel can hold it.

The call form follows the storage of the iterate, and residual!! selects it on the storage alone: with no buffer slot the call is F(x, p), for a Number, an MVector — which counts as a value — and an Array alike. J is the derivative of F, which jvp!! and jacobian!! read for the source nothing; AutoForwardDiff instead differentiates F. A method's own operator is a separate Jacobian source.

julia> prob = NonlinearProblem((x, p) -> x .* x .- 4);

julia> prob.F(3.0, nothing)
5.0

julia> prob.J === nothing
true

The storage seam

The storage seam lets an algorithm read each function's result rather than the storage itself, so the storage-specific operations stay at the leaves. Each function has a value method for a StaticArray or a Number iterate (R1) and an in-place method for an AbstractArray buffer slot (R3).

These names are not exported. Reach them as GeometricSolvers.name.

GeometricSolvers.buffer — Function
buffer(x)
buffer(x, TF, dims...)

One storage slot for an iterate like x, in the element type TF and with the shape dims. A caller creates slots during initialization; an algorithm consumes their returned values.

A value iterate — a StaticArray or a Number — has no slot: the call returns nothing, so the R1 state carries no buffer and spends no register on one. A static matrix is never an iterate and gets no slot either, which is why this method is written on StaticArray and not on StaticVector. An array iterate allocates a storage slot via similar.

source
GeometricSolvers.residual!! — Function
residual!!(y, prob, x, p)

The residual F(x, p) of prob at the iterate x, for the parameters p, in the storage of y, and return it.

y is the storage slot the residual is to occupy, and it alone selects the call form of the problem's F: with no buffer slot (nothing) the call is F(x, p), for an SVector, an MVector, a Number and an Array alike, because the iterate's type is read nowhere; with an array buffer slot y the call is F(y, x, p). There is no inplace flag that could disagree with the iterate, and no hasmethod.

This is the one function that moves the iterate, and the one seam a manifold solver extends: a retraction is a second method of it, and no algorithm changes.

Status and stopping test

Every type on this page is isbits, so a kernel can hold it, and every real field is in R = real(T) for the element type T of the iterate.

GeometricSolvers.ReturnCode — Type
ReturnCode

Why a solve or a step ended, stored in one byte so that a status fits a GPU register budget:

  • SUCCESS: the residual test of Options holds.
  • STALLED: the iterate or the residual stopped improving before the test held.
  • MAXITERS: the iteration cap was reached.
  • SINGULAR: a factorisation found a zero pivot; it reports this and does not throw.
  • NONFINITE: a residual, a step or a norm is not finite.
  • LINESEARCH_FAILED: the globalisation found no acceptable step.
source
GeometricSolvers.SolverStatus — Type
SolverStatus{R <: Real}

The result of a solve. It is isbits, so a kernel can write one per system, and every real field is in R = real(T) for the element type T of the iterate.

Fields

  • code::ReturnCode: why the solve ended.
  • iterations::Int32: the number of steps taken.
  • fnorm::R: $\|F(x)\|$ at return.
  • stepnorm::R: $\|Δx\|$ of the last step.
  • step_failures::Int32: every step-rule failure of the solve, such as a failed line search, in one count.
  • promoted::Bool: a factorisation ran in a higher precision than the factorisation precision of its method, after a stall or as a vendor fallback.

The predicates GeometricSolvers.isconverged and GeometricSolvers.isstalled read the code. They are not exported, because they are generic names that a package doing using GeometricSolvers may want for itself.

source
GeometricSolvers.StepInfo — Type
StepInfo{R <: Real}

The result of one step, which record folds into a SolverStatus.

Fields

  • code::ReturnCode: the outcome of the step.
  • fnorm::R: $\|F(x₊)\|$ at the new iterate, so that the loop needs no second reduction and, on a device, no second synchronisation.
  • stepnorm::R: $\|x₊ - x\|$.
  • failures::Int32: the step-rule failures inside this step, those of its members included.
  • promoted::Bool: the step factorised in a higher precision than its method's.
  • limited::Bool: the step was accepted, but a trust-region radius truncated it, so its norm is set by the radius and does not measure the distance to a root.
source
GeometricSolvers.Options — Type
Options{R <: Real}

The stopping test of the loop, and nothing else. It is isbits, and every tolerance is in R = real(T) for the element type T of the iterate, so a Float64 tolerance never reaches a Float32 kernel. The iteration cap of a line search is a field of the line search.

Fields

  • f_abstol::R, f_reltol::R: the residual test $\|F(x)\| ≤ \max(f_{abstol}, f_{reltol} \|F(x₀)\|)$.
  • x_abstol::R, x_reltol::R: the step test $\|Δx\| ≤ \max(x_{abstol}, x_{reltol} \|x\|)$.
  • min_iterations::Int32, max_iterations::Int32: the bounds on the number of steps.
  • max_stalls::Int32: the number of consecutive stalled steps after which the solve stops.

Options(T; kwargs...) builds one from the element type T of the iterate, so the caller never names R. A solve takes only an Options{R} for R = real(T) and raises an ArgumentError for any other: the tolerances of another precision do not carry over, because the Float64 default f_reltol = √eps(Float64) lies below eps(Float32) and a Float32 solve cannot reach it.

source
GeometricSolvers.Options — Method
Options(T; f_abstol, f_reltol, x_abstol, x_reltol, min_iterations, max_iterations, max_stalls)

Build the Options of a solve whose iterate has element type T, as Options{real(T)}. The two relative tolerances scale with eps(R):

keyworddefault
f_abstol0
f_reltol√eps(R)
x_abstol0
x_reltol2 eps(R)
min_iterations0
max_iterations100
max_stalls2

The default residual test is relative. The residual cannot fall below about $\mathrm{eps}(T) \|J\| \|x\|$, whatever the precision of the residual (Tisseur 2001, Cor. 2.5), and a default cannot know $\|J\| \|x\|$. So the default f_abstol is 0, which turns the absolute test off, and the relative test $f_{reltol} \|F(x₀)\|$ decides.

The stopping test runs before the first step, and min_iterations is 0. From a start at the limiting accuracy one Newton step makes the result worse (Wilkinson, quoted by Tisseur 2001). The relative test cannot see such a start: before the first step it compares $\|F(x₀)\|$ with a fraction of itself. So a start at the limiting accuracy returns unchanged after 0 iterations only when the caller sets f_abstol at or above its residual floor, as an integrator that knows the scale of F can.

A negative or NaN tolerance, a negative min_iterations, a max_iterations below min_iterations and a max_stalls below 1 raise an ArgumentError.

julia> opt = Options(ComplexF32; f_reltol = 1e-4);

julia> typeof(opt)
Options{Float32}

julia> opt.f_reltol
0.0001f0

Factorisation and solve

A linear-solver method enters a solve through init, factorize!! and ldiv!!. For a static matrix (R1) factorize!! and ldiv!! return new isbits values, so they run inside a kernel: StaticLU is LU with partial pivoting and Int32 pivots, StaticQR Householder QR without column pivoting, and StaticSVD a one-sided Jacobi singular value decomposition whose solve truncates at the rank cutoff √n · eps(TF) · σ₁, which is what makes a rank-revealing solve finite. For a vector state (R3) init pre-allocates DenseLU, DenseQR or DenseSVD, and factorize!! and ldiv!! reuse its buffers in place: through LAPACK on a host Array, and through KernelAbstractions on an AbstractGPUArray for DenseLU, DenseQR and DenseSVD. factorize!! states what a singular matrix gives. init is exported; the remaining names are not exported and are reached as GeometricSolvers.name.

GeometricSolvers.factorize!! — Function
factorize!!(fac, method, J)

Factorise the matrix J with the linear-solver method method and return the factors.

For a static matrix (R1), fac is nothing or an earlier factor of the same type, whose value is not used, and the result is a new StaticLU, StaticQR or StaticSVD. J is converted to the element type of the factors, factor_eltype. Where that is not the element type of J, J is first divided by the power of two 2^e that brings its largest |re| or |im| into [1, 2), or as close as the exponent range allows, and e is kept in the factor, so that the overall scale of J neither overflows nor underflows in the factor type. A zero or non-finite J gives e = 0. A singular J does not throw. LU records the first zero pivot in info, QR the first zero diagonal entry of R, and returncode then gives SINGULAR. QR is not rank-revealing: a singular J whose R has no exact zero on the diagonal gives SUCCESS, and two equal rows, as a rule, give no exact zero. The SVD records the first singular value that its rank cutoff √n · eps(TF) · σ₁ counts as zero, and it is prescaled at the working precision too, because the sweep squares the entries.

For a dense factor (R3), fac is a DenseLU, DenseQR or DenseSVD built by init. J is written into fac.factors, divided by 2^e as for a static matrix where its element type is not that of fac.factors, and fac.factors is factorised in place; J === fac.factors is factorised as it is. On a device DenseSVD, J is divided by 2^e unconditionally into fac.U before the one-sided Jacobi sweep. For DenseSVD, info is gesvd's non-convergence code on the host, or 1 when the device Jacobi sweep reaches its sweep cap without converging or meets a non-finite entry, and a rank deficiency gives info == 0 and SUCCESS. An Inf in a dense J does not throw, and the step that ldiv!! then gives is not specified.

A precision marker such as TF32 has no method for a static matrix: the call raises a MethodError.

source
GeometricSolvers.ldiv!! — Function
ldiv!!(d, fac, r)

Solve A d = r with the factors fac of A, and return d in the element type of r.

For a static factor (R1), d is nothing and the result is a new SVector. For a dense factor (R3), d is the vector buffer written in place and returned. Where the element type of r is the element type of the factors, the solve runs directly in it. Where they differ, a finite, nonzero r is scaled by s = maximum(abs, r), converted to the factor type, solved, converted back and multiplied by s (Kelley 2023, eqs. 2.17–2.18). Normalisation prevents overflow from the overall right-hand-side scale in a lower factor precision; entries small relative to the largest entry can still underflow. The scale takes no squares and overflows only where an entry's absolute value does. In the mixed-type path, a zero r returns a zero step without solving, and an Inf or NaN in r gives a non-finite step. In both paths the step is multiplied by 2^-e, the power of two that factorize!! divided J by, in the element type of r. The SVD's solve leaves out the directions that its rank cutoff counted as zero, so that a rank-deficient system gives a finite, truncated step rather than an enormous one.

GeometricSolvers.StaticSVD — Type
StaticSVD{N, TF, R, L}

The singular value decomposition of an N × N static matrix, in element type TF, computed by the one-sided Jacobi iteration of src/linear/static/svd.jl. factors holds U, V holds the right singular vectors as columns, and σ holds the N singular values in non-increasing order in R = real(TF). info is the index of the first singular value that the rank cutoff √N · eps(TF) · σ₁ counts as zero, or 0 where there is none, so that returncode gives SINGULAR for a rank-deficient matrix as it does for the LU and QR factors; the truncated directions are zeroed in U, and the solve of ldiv!! leaves their coordinates out. converged is false where the sweep reached its cap of 30 sweeps before the columns were orthogonal. scale_exponent is the exponent e of the power of two 2^e that the matrix was divided by, and σ holds the singular values of the matrix as it was passed, not of the scaled one: a σ₁ above floatmax(R) — every entry of the matrix finite — is not representable there, and σ then holds Inf. σ̂ holds the singular values of the scaled matrix, the ones the sweep computed and the ones the solve divides by, so that the limit of σ is the limit of the report alone and not of the step.

L = N * N makes the SMatrix fields concrete, so the factor is isbits.

Eigensolver

jacobi_eigen is a function on a matrix and not a linear-solver method: cyclic two-sided Jacobi for a Hermitian or a real symmetric matrix, on the rotations and the round-robin ordering of the Jacobi SVD with a Frobenius-norm pair floor eps(R) * ‖H‖_F, for the case jacobi_eigen(im * M) of a real skew M that the ProjectedSkew exponential algorithm of GeometricOptimizers needs. It adds no method to LinearAlgebra.eigen, because a method of eigen for a StaticArrays type would be type piracy.

GeometricSolvers.jacobi_eigen — Function
jacobi_eigen(A)

The eigenvalues and the eigenvectors of the Hermitian matrix A, or of a real symmetric one, by cyclic two-sided Jacobi: the rotations and the round-robin ordering of the Jacobi SVD of SVDFactorization, applied to the rows and the columns of A at once. The eigenvectors are unitary to working precision, which is what the ProjectedSkew exponential algorithm of GeometricOptimizers needs of them. A pair whose off-diagonal entry is at or below eps(real(eltype(A))) * ‖A‖_F is skipped, which is what ends the sweep on a rank-deficient or low-rank matrix, as the SVD's negligible-column guard ends its own.

The call returns (values, vectors, status): values holds the N eigenvalues in real(eltype(A)), vectors the columns of the unitary V with A = V * Diagonal(values) * V', and status is SUCCESS where the sweep reached its fixed point, or MAXITERS where it reached its cap of 30 sweeps first. All three are isbits, so the call runs inside a kernel.

The matrix is assumed Hermitian: the call reads its lower triangle and sets the upper triangle to the conjugate of the lower one on entry, so a matrix that is not Hermitian gives the eigensystem of that Hermitian part and not the one of A. A NaN or an Inf entry is not checked: nothing throws, and the sweep reaches its cap for N ≥ 2; at N = 1 there is no pair, so the call returns SUCCESS.

For a real skew matrix M, the Hermitian matrix is im * M, with the eigenvalues values of im * M and

exp(M) ≈ real(V * Diagonal(exp.(-im .* values)) * V')

to working precision — the ProjectedSkew case, which is what jacobi_eigen exists for.

Line searches

A line search is scalar code: linesearch sees the line only through the merit φ and its derivative φ′, allocates nothing and never throws, so the same search runs on the host and inside a kernel. Its iteration cap, where it has one, is its own field. Along a LineFunction its LineSearchResult also carries the residual at the step, so the caller does not evaluate it again.

GeometricSolvers.Backtracking — Type
Backtracking(; c₁ = 1e-4, p = 0.5, maxiter = 100)

The Armijo line search with a safeguarded quadratic and cubic interpolation step. It shrinks the trial step until the sufficient_decrease test

\[φ(α) - φ(0) ≤ \min\bigl(0,\ c_1 α φ′(0) + τ\bigr)\]

holds, where $τ$ is the roundoff of $φ(0)$. Each backtrack takes the minimiser of the model through $φ(0)$, $φ′(0)$ and the last one or two trials, clamped to $[0.1 α, p α]$. A trial whose merit is not finite gives no model; the next trial is then the smaller of $0.1 α$ and the geometric mean of $α$ and the step floor. The search stops at the step floor smallest_step, after two trials at steps below $\sqrt{\mathrm{eps}}$ whose merit equals $φ(0)$ bit for bit, or after maxiter trials.

The slope $φ′(0)$ comes from the step kind: $-2φ(0)$ for an ExactStep, one evaluation for a MeasuredSlope, the number itself for a slope passed in. For an InexactStep with residual $η$ the test is Eisenstat and Walker's $\|r(x + α d)\| ≤ [1 - c_1 (1 - η(α))] \|r\|$ with $η(α) = |1 - α| + α η$, and the model slope is $-2(1 - η) φ(0)$.

The model is built from differences of the merit divided by $|φ′(0)|$, and the cubic step uses the form that does not cancel on a near-quadratic merit, so the trials do not depend on the scale of the merit.

source
GeometricSolvers.Bisection — Type
Bisection(; αmax = 65536.0, maxiter = 100)

The line search that bisects $φ′$ for a minimiser of the merit along the line. It brackets from the anchor: the lower end starts at $0$, where $φ′(0) < 0$, and the upper end at the trial step, doubled while $φ′ < 0$, up to the smaller of its own αmax and the caller's. So the bracket always holds a sign change from $-$ to $+$: a minimum, never a maximum. A $φ′$ that is not finite counts as not descending, so the bracket never grows into a region where the merit is not finite.

It then bisects the bracket. While the bracket spans more than a factor 2, the next trial is the geometric mean of its ends, with a lower end of $0$ taken as the step floor smallest_step; after that it is the middle. It stops when the width is below $\sqrt{\mathrm{eps}}$ times the upper end, or when the lower end is still $0$ and the upper end is within a factor 2 of the floor. So the number of trials grows only with $\log_2 \log_2$ of the ratio of the trial step to the floor, and it stays bounded for αmax = Inf. While the lower end stays at $0$, a search from the trial step $α$ costs at most $3 + ⌈\log_2 \log_2(α / \mathrm{floatmin}(R))⌉$ evaluations, because the floor is at least floatmin(R): 10 in Float32 and 13 in Float64 for $α = 1$.

It returns the lower end of the bracket, where $φ′$ is finite and negative, its upper end if the lower end is $0$, or the ceiling if $φ′$ is still negative there, and classifies it by the merit there: one evaluation of $φ$ after one $φ′$ per trial.

source
GeometricSolvers.StrongWolfe — Type
StrongWolfe(; c₁ = 1e-4, c₂ = 0.9, αmax = 65536.0, maxiter = 100)

The line search for a step with the strong Wolfe conditions

\[φ(α) - φ(0) ≤ c_1 α φ′(0), \qquad |φ′(α)| ≤ c_2 |φ′(0)|,\]

$0 < c_1 < c_2 < 1$: Nocedal and Wright's Algorithms 3.5 and 3.6. The first condition is the sufficient_decrease test without a round-off allowance. The bracketing phase doubles the trial step up to the smaller of αmax and the caller's ceiling until a trial fails the first condition, does not decrease the merit, or has $φ′ ≥ 0$. The zoom phase then takes the minimiser of the cubic through the merit and its derivative at both ends of the bracket, or of the quadratic through both merits and the derivative at the lower end where the upper end has no derivative. The trial is safeguarded to the inner 80 % of the bracket, and it is the middle after a trial that shrinks the bracket by less than a factor 0.66, as in Moré and Thuente. The lower end is the trial with the lowest merit that meets the first condition, up to the roundoff of the larger of two merits: a trial within it of the lower end ties with it, and the sign of $φ′$ at the trial decides the side of the minimiser. A zoom trial that meets both conditions is accepted whatever its merit.

$φ′$ is evaluated only at a trial that meets the first condition and, in the bracketing phase, decreases the merit: a trial that fails costs one $φ$, a trial that passes one $φ$ and one $φ′$.

It returns SUCCESS only for a step that meets both conditions and decreases the merit by more than its round-off. Every other search returns its lowest trial that meets the first condition, or else its last trial. At the ceiling, at a collapsed bracket or at the step floor smallest_step the code is STALLED if the merit is at its round-off floor and LINESEARCH_FAILED otherwise; after maxiter trials it is LINESEARCH_FAILED.

A trust region is the other globalization of Newton. DogLeg is no line search: it needs the Jacobian, its factor and a radius that lives across iterations, so Newton keeps the radius in its state and runs the trial loop on the dogleg curve itself.

GeometricSolvers.DogLeg — Type
DogLeg(; radius = nothing)

The trust-region globalization of Newton on the dogleg curve: Newton(; globalization = DogLeg()). It is not a LineSearch: it needs the Jacobian, its factor and a radius that lives from one iteration to the next, so Newton holds the radius in its state and runs the trial loop with its own Jacobian.

The defaults are Procedure 4.1 of Pawlowski, Simonis, Walker and Shadid (2008). The step is the Newton step when it lies in the radius $δ$, else the Cauchy step along $-J^* F$ scaled to $δ$ when the Cauchy point lies outside $δ$, else the point of norm $δ$ on the segment from the Cauchy point to the Newton step. $J$ is the matrix that was factorised, regularisation included. A trial is accepted when the predicted reduction $\mathrm{pred} = \|F(x)\| - \|F(x) + J s\|$ is positive and the actual reduction $\mathrm{ared} = \|F(x)\| - \|F(x + s)\|$ satisfies $\mathrm{ared} ≥ 10^{-4} \mathrm{pred}$, with unsquared norms; a rejected trial shrinks $δ$ to $\max(δ/4, 10^{-6})$ and chooses again on the same curve, with no new Jacobian or solve. So a rejected Newton step that lies well inside $δ$ is tried again, at one evaluation of F each time, until $δ$ falls below its norm. A rejection at $δ = 10^{-6}$ returns LINESEARCH_FAILED with the iterate kept. After an accepted step with ratio $ρ = \mathrm{ared} / \mathrm{pred}$, $ρ < 0.1$ sets $δ$ to $\max(\|s^{N}\|, 10^{-6})$ when the Newton step $s^{N}$ is shorter than $δ$ and to $\max(δ/4, 10^{-6})$ otherwise, and $ρ > 0.75$ on the boundary sets it to $\min(4δ, 10^{10})$. An accepted step other than the whole Newton step sets limited in its StepInfo: the radius or the Cauchy point, not the distance to a root, sets its norm, so the solve applies only the residual test after it.

radius is the initial radius. It must be positive and finite as given; DogLeg stores it converted to float(typeof(radius)), and ToReal to the iterate's real type, clamped to $[10^{-6}, 10^{10}]$ after each conversion. With nothing, the first step starts the radius at the norm of the first Newton step, clamped the same way, except that a norm below $10^{-6}$ starts it at $2 \cdot 10^{-6}$, as Procedure 4.1 does. A singular factor, or a Newton step whose norm is not finite, gives no Newton step: the step is then the Cauchy point, cut to the radius when it lies outside, and a first radius starts at the length of the Cauchy point, by the same rule. The Cauchy direction is formed from the unit residual, $\tilde g = J^* F / \|F\|$, so no norm of $J^* F$ occurs, and a common scale of $F$ and $J$ leaves the Cauchy point unchanged up to rounding, as long as the norm of $\tilde g$ is finite. Where the Cauchy point is needed and $\tilde g$ is zero or its norm is not finite, or $J \tilde g / \|\tilde g\|$ is zero or its norm is not finite, the step returns STALLED with the iterate kept. At $F(x) = 0$ the step returns SUCCESS with the iterate and the radius kept, and makes no trial.

DogLeg takes no factor reuse: Newton(; globalization = DogLeg(), reuse = k) raises an ArgumentError.

A nonlinear solver holds its algorithmic configuration (linsolve, globalization, jacobian, refinement, regularization and reuse for Newton; damping and globalization for Picard) and nothing about the problem or the iterate. solve adapts the method to R = real(eltype(x₀)), calls init_state and solve!! on a copy of x₀ when x₀ is an array, and returns (x, status). GeometricSolvers.solve!! — Function
solve!!(state, prob::NonlinearProblem, x₀, method, p = nothing, options = Options(eltype(x₀)))

Run the nonlinear solver loop from x₀ using state = init_state(method, prob, x₀, p) and return (x, status, state). solve!! is the in-place and kernel entry point: inside a KernelAbstractions.@kernel, a caller prepares state₀ = init_state(m, prob, x₀, p) on the host and calls solve!!(state₀, prob, x_i, m, p_i, opt) in each work-item.

Every return goes through finish!!, and solve!! returns the triple that finish!! returns.

When the residual test of Options already holds at 0 iterations, it returns SUCCESS. When options.max_iterations == 0, it returns MAXITERS with 0 iterations. options must be an Options{real(eltype(x₀))}; any other raises an ArgumentError.

Inside the loop, each trip calls step!! and updates status via record. SINGULAR and NONFINITE return immediately. Automatic differentiation

In R1, prepare_ad returns the AutoForwardDiff() back end itself for a StaticVector or a Number iterate. jacobian!! and jvp!! run tagged ForwardDiff directly with that source. The source nothing calls the problem's own J; a JacobianFunction calls a method's operator for jacobian!! only. A back end other than AutoForwardDiff has no R1 method, and the call is a host MethodError.

In R3 the AD path is chosen once, by prepare_ad, from the back end and the storage of the iterate: AutoForwardDiff() goes through an own chunked forward mode on every array type, and any other back end goes through DifferentiationInterface on a CPU iterate, so every ADTypes back end works with no line of source here. A device array iterate takes AutoForwardDiff() only, because DifferentiationInterface's jacobian! raises a scalar-indexing error on an MtlArray, a CuArray and a JLArray. When the problem supplies an analytic 3-argument J(Jbuf, x, p), JacobianMatrixJVP evaluates prob.J into its pre-allocated matrix buffer and multiplies by the direction in place. Only a LineSearch other than Static takes a JVP, so under any other globalization the analytic J gets no JVP preparation and no second n × n buffer. jacobian!! and jvp!! then dispatch on the object the preparation returned, so the solver makes no runtime choice and carries no ad keyword.

In R3 the iterate is a vector; another shape raises ArgumentError where the preparation is built. The parameters may be replaced on every call, which is what lets one preparation serve a whole time-stepping loop.

AutoEnzyme reaches the Array path through DifferentiationInterface like any other back end, but it needs runtime activity for the parameter context — AutoEnzyme(; mode = Enzyme.set_runtime_activity(Enzyme.Forward)). A plain AutoEnzyme() raises EnzymeRuntimeActivityError on a residual that broadcasts constant parameters into its result; see KNOWN_ISSUES.md. The mode is the caller's choice, so the package sets none.

These names are not exported. Reach them as GeometricSolvers.name.

GeometricSolvers.LineSearch — Type
LineSearch{R}

The supertype of the line searches Static, Backtracking, Bisection and StrongWolfe, whose numbers are of the real type R. A line search is a method: it is isbits, it holds numbers and, except Static, an Int32 cap and nothing else, and linesearch runs it.

Every line search keeps six contracts:

  1. It never throws. A constructor checks its parameters on the host and raises an ArgumentError; linesearch raises nothing.
  2. It returns $α > 0$.
  3. It reports through the code of its LineSearchResult and never logs.
  4. A non-finite or ascending anchor is reported, not searched: NONFINITE and LINESEARCH_FAILED. A stationary anchor, $φ′(0) = 0$, is STALLED. Static is the exception: it reads no anchor and returns its step.
  5. Its number of evaluations does not depend on the scale of the merit.
  6. It returns $α ≤ α_{max}$, for the caller's αmax and for its own.

It never evaluates the merit at $α = 0$: the caller passes $φ(0)$, which is the residual it already has.

GeometricSolvers.InexactStep — Type
InexactStep(η)

The step kind of a direction d with the linear residual $\|r + J d\| ≤ η \|r\|$, $0 ≤ η < 1$. It gives only $φ′(0) ≤ -2(1 - η) φ(0)$ (Eisenstat and Walker 1996, (1.2)). Along $α d$ the linear residual is $(1 - α) r + α (r + J d)$, so its bound is $η(α) = |1 - α| + α η$. Backtracking tests $\|r(x + α d)\| ≤ [1 - c_1 (1 - η(α))] \|r\|$ with this $η(α)$, which for $α ≤ 1$ is the update $η ← 1 - θ (1 - η)$ of each backtrack by $θ$, and evaluates no $φ′$. A step with $η(α) ≥ 1$ promises no decrease and is rejected. Bisection and StrongWolfe need the true slope and evaluate $φ′(0)$. The constructor checks nothing, so that solver code can build one in a kernel: a search given an $η$ outside $[0, 1)$ evaluates nothing and returns LINESEARCH_FAILED. Static reads no step kind and returns its step.

sufficient_decrease(φα, φ₀, demand, τ)

The Armijo test on the difference, $φ(α) - φ(0) ≤ \min(0, \mathrm{demand} + τ)$, where demand is the negative decrease the test demands and $τ$ the round-off allowance. The difference keeps a demand below one ulp of $φ(0)$, which $φ(0) + \mathrm{demand}$ would round away; the min lets $τ$ lower the demand, never accept an increase. StrongWolfe passes $τ = 0$.

GeometricSolvers.backtrack_step — Function
backtrack_step(φ₀, d₀, α, φα, αp, φp, p)

The next trial step after the rejected trial α with merit φα; αp and φp are the trial before it, and αp is NaN on the first backtrack. The model of $φ$ is a quadratic through $φ(0)$, $φ′(0) = d_0$ and $φ(α)$, then a cubic through $φ(α_p)$ as well, both in the merit divided by $|d_0|$. The cubic minimiser is $1 / (b + \sqrt{b^2 + 3a})$ for $b > 0$, which does not cancel as $a → 0$. The result is clamped to $[0.1 α, p α]$; a model without a minimiser gives $p α$, and a merit that is not finite at α gives $0.1 α$.

GeometricSolvers.zoom_step — Function
zoom_step(a, φa, da, b, φb, db)

The minimiser of the cubic through the merit φa, φb and its derivative da, db at the two ends a and b of a bracket (Nocedal and Wright, (3.59)), clamped to the inner 80 % of the bracket. The discriminant is scaled by the largest of $|θ|$, $|d_a|$, $|d_b|$, as in Moré and Thuente, so it neither overflows nor depends on the scale of the merit. A cubic without a minimiser gives the middle of the bracket. Without a finite db it is the minimiser of the quadratic through φa, da and φb.

GeometricSolvers.LinearMethod — Type
LinearMethod{TF}

The supertype of the linear-solver methods. TF is the factorisation precision: Nothing for the working type of the problem, a real float type, or a PrecisionMarker. It is a type parameter and not a field, because a type stored in a field is not isbits, and a method must enter a kernel.

TF is a real type for a complex problem too: LUFactorization(Float32) factorises a ComplexF64 Jacobian in ComplexF32.

GeometricSolvers.jacobi_rotation — Function
jacobi_rotation(α, β, γ)

The rotation (cs, sn) that makes the Hermitian 2 × 2 matrix [α γ; γ̄ β] diagonal, with real α and β: with G = [cs sn; -conj(sn) cs], the product Gᴴ [α γ; γ̄ β] G is diagonal, and θ with tan θ = t is at most π/4 in modulus, which is what makes the sweep converge rather than merely rearrange.

γ must not be zero: the phase of the rotation is γ / |γ|.

GeometricSolvers.converged — Function
converged(options::Options{R}, status::SolverStatus{R}, fnorm₀::R, xnorm::R)

The stopping test of Options at status, for a start with residual norm fnorm₀ and an iterate of norm xnorm. It holds once min_iterations steps are taken and either the residual test or, after a step of nonzero norm, the step test holds. At 0 iterations it is the test before the first step: the relative residual test then holds only for $F(x₀) = 0$, so a start passes it through f_abstol. A zero step is no progress, so it never passes the step test.

solve!! returns SUCCESS only through the residual test: a step test that holds while the residual test fails returns STALLED.

GeometricSolvers.rnorm — Function
rnorm(a)

The Euclidean norm $\sqrt{\sum_i |a_i|^2}$ in real(eltype(a)).

It scales the entries by $2^{-e}$, where $2^e$ is the power of two of the largest $|a_i|$ (of the largest real or imaginary part for a complex a), so that it neither overflows where the norm is finite nor underflows to zero where the norm is positive. The scale is exact and adds no rounding: where no square leaves the floating-point range, scaled or not, the result can differ from sqrt(norm2(a)) only in the last bits, through the order in which sum adds the squares. It takes two reductions, the largest entry and the sum. A NaN entry gives NaN, an Inf entry and no NaN gives Inf. Where real(eltype(a)) is no AbstractFloat, such as an integer or a ForwardDiff.Dual, it is the unscaled sqrt(norm2(a)).
