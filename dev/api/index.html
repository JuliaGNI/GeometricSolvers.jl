API

The problem

A problem holds functions and, for a NonlinearProblem, an optional Jacobian prototype: the residual, optionally its derivative, and optionally jacobian_prototype for a sparse R3 Jacobian in NonlinearProblem; the residual, optionally its derivative, and its length in LeastSquaresProblem; or the scalar action, its equation and unknown index sets, and an optional datum in StationarityProblem. Reparametrized wraps a NonlinearProblem or a StationarityProblem in a coordinate chart x = g(y, p), and Deflated wraps either in a deflation of the roots it is given, so that a solve from the same start converges to another root. BlockEliminated partitions the unknowns of a NonlinearProblem or a StationarityProblem into inner unknowns y = x[Y] and outer unknowns z = x[Z], eliminates y at each outer iterate by solving the inner equations, and steps on the outer equations with the Schur complement J_zz - J_zy J_yy⁺ J_yz; VariableProjection does the same for a LeastSquaresProblem across all m residual rows by Golub–Pereyra variable projection or Kaufman's reduced Jacobian (BlockEliminated on a LeastSquaresProblem forwards to VariableProjection). The storage of the iterate selects the call form of the functions, so one problem serves every regime. NonlinearProblem, StationarityProblem, LeastSquaresProblem, Reparametrized, Deflated, BlockEliminated and VariableProjection are exported; GeometricSolvers.jacobian_prototype and GeometricSolvers.jacobian_pattern are internal accessors.

GeometricSolvers.AbstractNonlinearProblem — Type
AbstractNonlinearProblem

The supertype of the problems a NonlinearSolver solves: NonlinearProblem, whose residual has as many entries as the iterate has variables, StationarityProblem, whose residual is a part of the gradient of a scalar action, and LeastSquaresProblem, whose residual may have more entries than the iterate has variables. init, solve, solve! and solve!! take it, and so does Newton with each of its globalizations, so one solver loop serves every problem type; Picard, the combinators Additive, Multiplicative, Repeat and Switch, and solve_batch! take a NonlinearProblem or a StationarityProblem, and a combinator raises an ArgumentError for a LeastSquaresProblem.

GeometricSolvers.NonlinearProblem — Type
NonlinearProblem(F; jacobian_prototype = nothing)
NonlinearProblem(F, J; jacobian_prototype = nothing)
NonlinearProblem(F, J; jacobian_prototype = nothing,
    block_residuals = nothing, block_jacobians = nothing)

The residual F of a nonlinear system, optionally its derivative J, and optionally a matrix jacobian_prototype giving the storage type and sparsity pattern of the Jacobian. With no prototype (jacobian_prototype = nothing), the problem holds functions only — no parameters, no iterate and no flag — so it is isbits when F and J are and a kernel can hold it.

With block_residuals given, the problem also carries one local residual F_i!(f_i, x_i, x, p) per block of a BlockPartition — writing the residual of block i on its own index set into f_i, reading external couplings from the frozen full iterate x — and optionally one block Jacobian J_i!(J_i, x_i, x, p) per block, and its F is the BlockResidual that holds them. J stays as the caller gives it; RAS reads the block functions and every other method the global ones. block_jacobians without block_residuals, and the two of different lengths, raise an ArgumentError.

The call form follows the storage of the iterate, and residual!! selects it on the storage alone: with no buffer slot the call is F(x, p), for a Number, an MVector — which counts as a value — and an Array alike. J is the derivative of F, which jvp!! and jacobian!! read for the source nothing; AutoForwardDiff instead differentiates F. A method's own operator is a separate Jacobian source. When jacobian_prototype is a SparseMatrixCSC, Newton allocates its Jacobian buffer and linear factorisation from that pattern and AutoSparse uses its sparsity pattern directly. A linear solver exists only for a real host Vector iterate with a SparseMatrixCSC{<:Any, Int} prototype, with Sparspak loaded and an LUFactorization in the iterate's element type; a QRFactorization, an SVDFactorization and a dense prototype raise MethodError when Newton initialises. On a device iterate, Newton(; jacobian = nothing) raises MethodError from the factor, with an analytic J or without, and an AutoSparse jacobian raises ArgumentError in prepare_ad first, as any back end other than AutoForwardDiff() does. Picard and a static or batched iterate ignore the prototype.

julia> prob = NonlinearProblem((x, p) -> x .* x .- 4);

julia> prob.F(3.0, nothing)
5.0

julia> prob.J === nothing && prob.jacobian_prototype === nothing
true

GeometricSolvers.StationarityProblem — Type
StationarityProblem(S; E = :, U = :, b = nothing)
StationarityProblem(S, E, U, b = nothing)

A stationarity problem (∇S(x, p))_E + b = 0 for the unknown entries x[U] of a state x, with scalar action S(x, p), stationarity-equation index set E, unknown index set U, and optional datum b.

The residual and its Jacobian are

\[F_a(u, p) = \frac{\partial S}{\partial x_{E_a}}(x(u), p) + b_a, \qquad J_{a, c}(u, p) = \frac{\partial^2 S}{\partial x_{E_a}\,\partial x_{U_c}}(x(u), p), \qquad a, c \in \{1, \dots, |E|\},\]

where $x(u)_i = u_c$ for $i = U_c$ and $x(u)_i = (x_0)_i$ for $i \notin U$. The action S(x, p) is never used as a line-search or trust-region merit function: the merit is always $\|F\|_2^2 = \|(\nabla S)_E + b\|_2^2$, because stationarity points of physical actions include saddle points where $S$ is indefinite.

Where E == U, J is a block of the Hessian of S and is symmetric. For other index sets it is not symmetric in general, so LDLTFactorization, which reads only the lower triangle, does not apply, and LUFactorization or QRFactorization does.

The state x must be real. For a complex state the default automatic differentiation raises an error: an ArgumentError from ForwardDiff for an array iterate, and a MethodError for an R1 iterate. A StationarityProblem has no implicit differentiation: init, solve, solve! and solve_batch! raise an ArgumentError for a ForwardDiff.Dual in the iterate or in p.

Arguments

  • S: a scalar callable S(x, p) returning a scalar in the element type of x.
  • E: : (all indices 1:length(x₀)) or a duplicate-free collection of positive integer indices (Tuple, SVector, AbstractUnitRange, or AbstractVector{<:Integer}). A Tuple of integers is converted to SVector{N, Int} so an R1 problem is isbits. An R1 iterate (a StaticVector or a Number) takes :, a Tuple or an SVector, and any other index set raises an ArgumentError at the solve.
  • U: : or a duplicate-free collection of positive integer indices of the same length as E. E and U are both : or both index sets.
  • b: nothing (zero datum), a vector of length |E|, a Number, or a callable b(p) returning a vector of length |E| or a Number. The keyword b on init, solve, solve! and solve_batch! overrides prob.b for that solve; in solve_batch! a PerSystem b gives system i the datum b.data[i].

LeastSquaresProblem(F)

LeastSquaresProblem(F, J = nothing; output_length = nothing)

A nonlinear least-squares problem $\min_x \tfrac{1}{2}\|F(x, p)\|_2^2$ with residual F of length $m$ in $n$ variables ($m \ge n$) and optional Jacobian J.

For out-of-place problems (SVector or Number), $m$ is inferred from F(x, p) and the field output_length may be nothing. For in-place problems (F(r, x, p) on mutable arrays), output_length is required and must satisfy m >= 1 and m >= length(x).

A LeastSquaresProblem holds no Jacobian prototype, so its Jacobian is dense. It has no implicit differentiation: solve with a ForwardDiff.Dual in x₀ or p raises an ArgumentError, as init and solve! do for every problem.

GeometricSolvers.Reparametrized — Type
Reparametrized(prob, g, ∂g = nothing;
               covariant = prob isa StationarityProblem, curvature = true)

Coordinate-chart wrapper x = g(y, p) around an AbstractNonlinearProblem prob (NonlinearProblem or StationarityProblem).

Solving a Reparametrized problem iterates in the chart coordinates y. solve and init / solve! return (x*, status) and solve!! returns (x*, status, state), where x* = g(y*, p) is evaluated at the returned chart iterate y*; solve_batch! writes each system's x* into the batch. For a StationarityProblem, the keyword b of init and solve sets the datum of the inner problem, as it does without the chart; with any other inner problem, b raises an ArgumentError.

Arguments and keywords

  • prob: the inner NonlinearProblem or StationarityProblem in x-coordinates. A StationarityProblem needs U = : or U = 1:n in order, for the chart dimension n, and E = : or a permutation of 1:n; init, solve, solve_batch! and prepare_ad raise an ArgumentError for any other index set. For an R1 iterate the index sets are :, a tuple or an SVector, as for a StationarityProblem without a chart, so a range such as 1:n raises an ArgumentError there.
  • g: the chart map x = g(y, p) in R1 (StaticVector or Number) or g!(x, y, p) in R3 (AbstractVector).
  • ∂g = nothing: optional chart Jacobian G = ∂g(y, p) in R1 or ∂g!(G, y, p) in R3. When ∂g === nothing, G(y, p) = ∂g/∂y is computed by forward-mode automatic differentiation.
  • covariant::Bool: when false (default for NonlinearProblem), the transformed residual and Jacobian are $\tilde{F}(y, p) = F(g(y, p), p)$ and $\tilde{J}(y, p) = J(g(y, p), p) G(y, p)$. When true (default for StationarityProblem), the residual is pulled back covariantly as $\tilde{F}(y, p) = G(y, p)^\top F(g(y, p), p)$.
  • curvature::Bool = true: when covariant == true, includes the chart-curvature term $(\partial G^\top / \partial y) F(g(y, p), p)$ in $\tilde{J}(y, p) = G^\top J G + (\partial G^\top / \partial y) F$ when true, or uses the pull-back approximation $\tilde{J}(y, p) = G^\top J G$ when false.

GeometricSolvers.Deflated — Type
Deflated(prob, roots; power = 2, shift = 1)
Deflated(prob, roots, power, shift)

Shifted norm deflation of the known roots roots around NonlinearProblem or StationarityProblem prob: the problem whose residual is

\[F_{\mathrm{def}}(x) = M(x) F(x), \qquad M(x) = \prod_{i=1}^{k} \left( \|x - r_i\|_2^{-p} + \sigma \right),\]

and whose Jacobian is the product rule of that product,

\[J_{\mathrm{def}}(x) = M(x) J(x) + F(x) \nabla M(x)^\top,\]

so that Newton started from the same x₀ converges to a root other than r₁, …, r_k (Farrell, Birkisson and Funke 2015, Deflation techniques for finding distinct solutions of nonlinear partial differential equations). Near a simple root ‖M(x) F(x)‖ grows like ‖x - rᵢ‖^{1-p}, which is what pushes the iterate away from it.

The steps and the line search take the deflated residual, but the stopping test of Options reads the inner one: status.fnorm is ‖F(x)‖, f_abstol bounds it, and f_reltol is relative to ‖F(x₀)‖, so a deflated root meets the tolerance of a solve of prob.

power (p > 0) and shift (σ > 0) are stored in T = float(real(eltype(first(roots)))), so Float32 roots give power::Float32 and a Float32 product; a solve needs an iterate of that element type and a real one.

Roots

roots is a non-empty Tuple of roots — a Number for a Number iterate, an SVector for an R1 iterate, an array of the iterate's own back end for an R3 iterate (a Vector for a Vector, a JLArray or an MtlArray for one on that device) — or an AbstractVector of real vectors. Every root has the length of the iterate and finite real entries, and the roots of one set share their element type and are all numbers or all vectors. A solve on an array iterate raises an ArgumentError for a root on another back end or a static root, because the deflation broadcasts x .- r on the iterate's back end. The AbstractVector form is not isbits, so solve_batch! refuses it: the batch kernel takes the problem by value.

For a wrapped StationarityProblem a root is a full state, as solve returns it, and the distance is taken on the unknowns x_U: M and ∇M are functions of the |U| entries the solve steps on, so ∇M has length |U| whatever the length of the state.

Evaluation

At a deflated root (x = rᵢ) the factor mᵢ is Inf, so a solve from x₀ = rᵢ returns NONFINITE at 0 iterations, and a trial step onto rᵢ has a non-finite merit, which Backtracking shrinks away from by the step min(0.1α, √α √αmin). A factor that overflows (‖x - rᵢ‖^{-p} = Inf, as at 10^{-200} in Float64) does the same. Every coordinate of ∇mᵢ is evaluated unit-scaled, -(p ((uⱼ/d) ϕ)/d) with d = ‖u‖ and ϕ = d^{-p}, which forms no ϕ/d² and so leaves no NaN where uⱼ is zero: the unscaled -(p ϕ/d²) uⱼ overflows to Inf at d = 10^{-100} and gives Inf * 0.0 = NaN there. Where ‖u‖^{-p-1} overflows although ‖u‖^{-p} does not (between about 10^{-155} and 10^{-103} in Float64 for p = 2), ∇mᵢ has an infinite coordinate and the Jacobian is not finite.

A Newton with a callable jacobian raises an ArgumentError, because Newton would take it as the deflated Jacobian. Give an analytic Jacobian of F to the wrapped NonlinearProblem instead.

Implicit differentiation

solve on a Deflated(NonlinearProblem) with a ForwardDiff.Dual in x₀ or p runs the primal deflated solve and differentiates the undeflated prob implicitly at the root it found, as solve does on the problem itself. A Deflated(StationarityProblem) refuses a dual with an ArgumentError, as a StationarityProblem does.

R2

solve_batch! solves every system of a batch under one Deflated, so each system is deflated at the same roots and ends at a root distinct from them. The batch of a wrapped StationarityProblem takes the datum of its solves from the keyword b, shared or PerSystem, or from the problem's own b.

julia> prob = NonlinearProblem((x, p) -> x^3 - x);

julia> def = Deflated(prob, (0.0,));

julia> solve(def, 0.1, Newton())[1] ≈ 1 || solve(def, 0.1, Newton())[1] ≈ -1
true

julia> solve(Deflated(prob, (0.0,)), 0.0, Newton())[2].code === NONFINITE
true

GeometricSolvers.BlockEliminated — Type
BlockEliminated(prob, inner; outer = nothing, inner_eqs = inner, outer_eqs = outer,
                inner_method = Newton(; linsolve = SVDFactorization()),
                linear_inner = false, inner_options = nothing)

Partition the unknowns x of a NonlinearProblem or StationarityProblem prob into inner indices Y = inner (y = x[Y]) and outer indices Z = outer (z = x[Z], defaulting to the complement of inner in 1:n), and the residual equations into inner equations E_y = inner_eqs and outer equations E_z = outer_eqs (|E_y| == |Y|, |E_z| == |Z|). The default outer_eqs = outer takes the outer unknown indices as equation indices, so give outer_eqs whenever inner_eqs differs from inner. On a LeastSquaresProblem, BlockEliminated(prob, inner; kwargs...) forwards to VariableProjection.

At each outer iterate z, the inner equations $F_{E_y}(y, z) = 0$ are solved for $y^*(z)$: in one linear solve $y^*(z) = -J_{yy}(0, z)^+ F_{E_y}(0, z)$ when linear_inner = true, or from the previous inner solution y_warm when linear_inner = false, with the adaptive tolerance $\tau_{\text{inner}} = \max(10\,\varepsilon\max(1, \|F_{E_y}^0\|_2), \min(c, 0.5 \|F_{E_z}(\text{prev})\|_2^2))$, where $c$ is the tolerance cap of inner_options (unbounded when they are nothing) and $\|F_{E_y}^0\|_2$ is the inner residual at the warm start. The cap stands alone before the first outer residual exists, so the tolerance is $\max(10\,\varepsilon\max(1, \|F_{E_y}^0\|_2), c)$ with inner_options and the floor alone without them. The inner iteration is Newton's method with step halving (at most 8 halvings per step) and at most max_iterations steps of inner_options (50 without them); inner_method supplies only the linear solver of these steps and of the Schur complement (inner_method.linsolve for a Newton, or a linear method itself). The outer solver then steps on the reduced residual $F_{\text{red}}(z) = F_{E_z}(\tilde y(z), z)$, where for linear_inner = false and an inner residual above the floor $\tilde y(z) = y - J_{yy}(y, z)^+ F_{E_y}(y, z)$ is the inner iterate y refined by one Newton correction (it agrees with $F_{E_z}(y^*(z), z)$ to first order in $F_{E_y}$), and otherwise $\tilde y = y$; the outer Jacobian is the Schur complement

\[S(z) = J_{zz}(y^*(z), z) - J_{zy}(y^*(z), z)\, J_{yy}(y^*(z), z)^+\, J_{yz}(y^*(z), z).\]

At return, $x^*[Y] = y^*(z^*)$ and $x^*[Z] = z^*$. Any inner solver failure or rank-deficient inner Jacobian (fac_yy.rank < |Y| under SVD) increments status.step_failures. The linear solve of linear_inner = true solves the inner equations only when they are affine in y: an inner residual $\|F_{E_y}(y^*(z), z)\|_2$ above $\sqrt{\varepsilon}\max(1, \|F_{E_y}(0, z)\|_2)$ also counts as an inner failure, and the solve goes on.

GeometricSolvers.VariableProjection — Type
VariableProjection(prob::LeastSquaresProblem, inner; outer = nothing,
                   linsolve = SVDFactorization(), jacobian_mode = :kaufman,
                   linear_inner = true,
                   inner_method = GaussNewton(; linsolve = SVDFactorization()),
                   inner_options = nothing)

Golub–Pereyra variable projection for a LeastSquaresProblem prob, partitioning the unknowns x into inner (linear or fast) parameters Y = inner (y = x[Y]) and outer parameters Z = outer (z = x[Z], defaulting to the complement of inner in 1:n) across all m residual rows.

For each outer iterate z, the inner subproblem $\min_y \tfrac{1}{2}\|r(y, z)\|_2^2$ is solved for $y^*(z)$ (in one linear least-squares solve $y^*(z) = -\Phi(z)^+ r(0, z)$ with $\Phi(z) = \partial r / \partial y$ when linear_inner = true, or by a Gauss–Newton iteration with step halving, warm-started from y_warm, when linear_inner = false). linsolve factorises $\Phi(z)$ when linear_inner = true; with linear_inner = false the linear solver of inner_method (inner_method.linsolve for a Newton, or a linear method itself) does, in the iteration and in the reduced Jacobian. The outer solver steps on the reduced residual $r_{\text{red}}(z) = r(y^*(z), z)$ with reduced Jacobian (m × |Z|):

  • jacobian_mode = :kaufman (default): Kaufman's first-term reduced Jacobian $J_{\text{red}}(z) = (I - \Phi(z)\Phi(z)^+) D(z)$, where $D(z) = \partial r(y^*(z), z)/\partial z$.
  • jacobian_mode = :golub_pereyra: the full Golub–Pereyra reduced Jacobian $J_{\text{red}}(z) = (I - \Phi(z)\Phi(z)^+) D(z) - (\Phi(z)^+)^H (\partial\Phi/\partial z)^H r_{\text{red}}(z)$.

Any inner solver failure or rank-deficient $\Phi$ increments status.step_failures. The linear solve of linear_inner = true minimises over y only when r is affine in y: an inner gradient $\|\Phi(y^*)^H r(y^*, z)\|_2$ above $\sqrt{\varepsilon}\max(1, \|r(0, z)\|_2)\max(1, \|\Phi(y^*)\|_F)$ also counts as an inner failure, and the solve goes on.

Reduced-space elimination with a batch inside the residual

BatchEliminated eliminates a whole batch of independent inner systems from the residual of an outer matrix-free Newton, rather than a block of one unknown vector: the outer solver steps on the m-vector alone, and every evaluation of that residual — the Krylov products of the outer step included — solves the batch and deposits its moments. It is the pattern of the implicit PIC method (Chen2011, pp. 7025 and 7033; LanzkronRoseWilkes:1996), where the outer Newton works on the field and the per-particle orbit solves are the eliminated unknowns. The inner tolerance of each evaluation is the adaptive quadratic $\max(2\varepsilon(R_{\text{in}}), R_{\text{in}}(\tfrac{1}{2}\min(c, \|g_2(\text{prev})\|^2)/\sqrt{N_p}))$, the batch is warm-started from the previous evaluation — so a second evaluation at the same iterate and tolerance takes 0 inner iterations — and the outer Jacobian–vector product is a one-sided difference at the step $\varepsilon \max(1, \|x\|)/\|v\|$, with the relative step $\varepsilon = \sqrt{\operatorname{eps}(R_{\text{eff}})}$ of the coarser of the two precisions, so that a Float32 batch inside a Float64 outer solve converges at the tolerance its own accuracy supports and, below it, ends on a stall rather than on a factorisation failure — on the problem of make_pic_elimination_problem, the solve at 2e-4 returns SUCCESS and the one at 1e-10 STALLED. The batch's BatchSummary reports its global residual norm, whether every system converged, and how many did not; deposited_moments returns what the deposit wrote, and reset_batch! returns the problem to its initial state. make_pic_elimination_problem builds the one-dimensional implicit electrostatic PIC test problem that the elimination checks solve.

GeometricSolvers.BatchEliminated — Type
BatchEliminated(outer_F!, inner_prob, Y₀, deposit!, moments; per_system = nothing,
                inner_method = Newton(), inner_options = nothing,
                inner_atol_cap = 1e-2, eliminated_indices = nothing,
                workgroupsize = 64)

Reduced-space nonlinear elimination with an R2 batch inside the outer residual: the outer solver steps on the m-vector that outer_F! returns, and every evaluation of that residual — the Jacobian–vector products of a matrix-free outer Newton included — solves the whole batch of length(Y₀) independent inner systems and deposits its moments.

inner_prob is the NonlinearProblem of one inner system, solved for every system by solve_batch! from the batch's warm start Y, which the problem keeps in place across outer evaluations; Y₀ is the initial batch state and is never mutated, and Y is a host Vector copy of it, so the batch runs on the CPU backend whatever the array type of Y₀; per_system is the indexable per-system data of the batch, or nothing for a batch whose systems share all their parameters. deposit!(moments, Y, shared, per_system) fills moments from the batch Y and the shared parameter, and outer_F!(F_out, x, moments, shared) writes the outer residual at x — where shared is the outer iterate converted to real(eltype(eltype(Y₀))), which is what every system of the batch gathers. eliminated_indices are the indices of the eliminated unknowns in the stacked unknown vector, one for each entry of every system, 1:sum(length, Y₀) by default; a set of another length is a DimensionMismatch.

The inner tolerance of the batch at one outer evaluation is the adaptive quadratic one of LanzkronRoseWilkes:1996 (Thm 5.4 and Cor 5.5),

\[f_{\text{abstol},p} = \max\left(2\varepsilon(R_{\text{in}}), R_{\text{in}}\left(\tfrac{1}{2}\min(\texttt{inner\_atol\_cap}, \|g_2(\text{prev})\|^2) / \sqrt{N_p}\right)\right),\]

so that the batch residual satisfies $\|g_1\| < \|g_2(\text{prev})\|^2$ wherever $\|g_2(\text{prev})\|^2 > 4\,\varepsilon(R_{\text{in}})\sqrt{N_p}$. Below that bound the floor binds: no arithmetic in R_in reaches the quadratic, and the batch residual stops at the floor of the batch's own precision instead of following the schedule. Each evaluation records the pair (‖g₁‖, ‖g₂(prev)‖) in the fields g₁_history and g₂_prev_history, with Inf before the first outer residual exists, the index set it eliminated in eliminated_index_log, and accumulates its inner counts in statuses. A batch whose systems did not all converge, with a residual above the coarse ceiling $32\,\varepsilon(R_{\text{in}})\sqrt{N_p}$, has no value to deposit: the residual of that evaluation is NaN and the outer solve cannot step on it. Under the ceiling the batch has stopped at the floor of its own arithmetic instead, and its deposit stands. The next evaluation takes the cap as its tolerance when the previous residual is not finite, since such a residual narrows nothing. reset_batch! returns the batch to Y₀ and the records to empty.

A second evaluation at the same (x, tolerance) reports 0 inner iterations for every system: the batch state is the root of the first one, and residual!!(F_out, prob, x, p; repeat_same_tol = true) re-uses the tolerance of the previous evaluation instead of narrowing it.

The outer Jacobian–vector product is a one-sided difference with the step $h = \varepsilon \max(1, \|x\|)/\|v\|$, scaled by the iterate and the direction, and the relative step $\varepsilon = \sqrt{\operatorname{eps}(R_{\text{eff}})}$, R_eff the coarser of the batch's and the outer iterate's element type (ChenChaconBarnes:2012, p. 5384): a Float32 batch inside a Float64 outer solve converges at the outer tolerance that the batch's accuracy supports and stalls, rather than failing, below it. Both evaluations of the difference are solved at the batch's own floor 2 eps(R_in), so the difference is the field's response and not the tolerance's, and the batch returns to prob.Y_anchor afterwards. The outer Newton takes jacobian = nothing or AutoForwardDiff() for this difference, or a JVPFunction of its own, and a GMRES without a jvp_eltype; any other back end, and a jvp_eltype, is an ArgumentError.

Status and stopping test

Every type on this page is isbits, so a kernel can hold it, and every real field is in R = real(T) for the element type T of the iterate. SolverStatus also carries the range and spectrum diagnostics (rank, nullnorm and gradratio) recorded at the iterate $x_k$ of the last fresh Newton factorisation, not at the iterate $x$ at return; a solve of a LeastSquaresProblem that ends on the stationarity test has factorised afresh at the iterate it returns. With regularization = μ ≠ 0, rank and nullnorm describe $J(x_k) + μ I$ and gradratio describes $J(x_k)$, so the classification below holds for μ = 0 only. For n ≥ 2 (for n = 1, a nonzero scalar Jacobian always gives gradratio = 1, and rank = 1 with an SVD factor), they classify the outcome and a STALLED or MAXITERS return: a consistent rank-deficient system that converged has a small residual (fnorm small) and nothing outside the range (rank < n, nullnorm ≈ 0); a least-squares point with no root has gradratio ≈ 0 (fnorm > 0) and the residual outside the range (rank < n, $\text{nullnorm} \approx \|F(x_k)\| > 0$); a stall in nearly singular directions has the residual inside the range (nullnorm ≈ 0) at a fine SVD cutoff and outside it (rank < n, $\text{nullnorm} \approx \|F(x_k)\|$) at a coarse one; and an in-range stall from conditioning or step acceptance has gradratio bounded away from zero with nullnorm ≈ 0.

GeometricSolvers.SolverStatus — Type

Fields

  • step_failures::Int32: every step-rule failure of the solve, such as a failed line search, in one count.
  • promoted::Bool: a factorisation ran in a higher precision than the factorisation precision of its method, after a stall or as a vendor fallback.

Factorisation and solve

A linear-solver method enters a solve through init_linear (and dense_factor), factorize!! and ldiv!!. For a static matrix (R1) factorize!! and ldiv!! return new isbits values, so they run inside a kernel: StaticLU is LU with partial pivoting and Int32 pivots, StaticLDLT is Bunch–Kaufman L D Lᵀ / L D Lᴴ with 1×1 and 2×2 diagonal blocks, StaticQR and StaticRectQR are Householder QR without column pivoting, and StaticSVD and StaticRectSVD are a one-sided Jacobi singular value decomposition whose solve truncates at the rank cutoff √n · eps(TF) · σ₁ for a square matrix and √m · eps(TF) · σ₁ for a rectangular one, m its row count, which is what makes a rank-revealing solve finite. For a vector state (R3) with no sparse pattern (jacobian_pattern(prob, jacprep) === nothing), init_linear pre-allocates DenseLU, DenseLDLT, DenseQR or DenseSVD on a host Array and DeviceLU, DeviceLDLT, DeviceQR or DeviceSVD on an AbstractGPUArray, and factorize!! and ldiv!! reuse its buffers in place: through LAPACK on the host, and on a device through the GeometricSolversMetalExt (Metal MPS lu! and ldiv! on MtlMatrix{Float32} and MtlVector{Float32}, with every MPS failure status reported as a singular factor) and GeometricSolversCUDAExt (CUDA cuSOLVER getrf!, getrs!, geqrf!, ormqr! with cuBLAS trsv!, and gesvdj! on CuMatrix{T} and CuVector{T} for T <: LinearAlgebra.BlasFloat, falling back to ka_factorize_svd! where gesvdj! does not converge) package extensions where available and through KernelAbstractions otherwise. When Sparspak is loaded and jacobian_pattern is a SparseMatrixCSC{<:Any, Int} on a host Vector{T} (T <: AbstractFloat) — from an explicit jacobian_prototype, or detected automatically by GeometricSolversSparseADExt when SparseMatrixColorings is loaded — the GeometricSolversSparspakExt package extension pre-allocates a SparspakLU workspace and unfactorised Sparspak.SparseSolver in init_linear for an LUFactorization whose factor element type is T (LUFactorization() or LUFactorization(T)); the first factorize!! call runs symbolic ordering and symbolic factorisation, and subsequent factorize!! and ldiv!! calls reuse them across Newton steps. That configuration is the only one with a sparse factor, and has_sparse_factor names it. A detected pattern is used only where has_sparse_factor holds and, under a Newton regularization ≠ 0, only where the pattern holds the whole structural diagonal. Everywhere else — QRFactorization, SVDFactorization, mixed precision such as LUFactorization(Float64) on a Float32 iterate, a complex iterate, or no Sparspak — a detected pattern gives the dense factor and a dense Jacobian buffer, as a solve with no pattern does. An explicit jacobian_prototype outside that configuration raises an error in init_linear or at the first factorize!!. A LeastSquaresProblem takes no detected pattern, because SparspakLU is square: its m × n factor is dense. factorize!! states what a singular matrix gives: an SVD factor records its numerical rank in rank apart from its status, and exact_solve tells Newton whether the solve is exact or truncated; singular_values gives the singular values of a StaticSVD or StaticRectSVD. These names are not exported and are reached as GeometricSolvers.name.

GeometricSolvers.factorize!! — Function
factorize!!(fac, method, J)

Factorise the matrix J with the linear-solver method method and return the factors.

For a static matrix (R1), fac is nothing or an earlier factor of the same type, whose value is not used, and the result is a new StaticLU, StaticQR, StaticSVD or StaticLDLT for a square J, and a StaticRectQR or StaticRectSVD for the QR or SVD of an M × N matrix with M > N (the LU and the LDLᵀ have no rectangular method). J is converted to the element type of the factors, factor_eltype. Where that is not the element type of J, J is first divided by the power of two 2^e that brings its largest |re| or |im| into [1, 2), or as close as the exponent range allows, and e is kept in the factor, so that the overall scale of J neither overflows nor underflows in the factor type. A zero or non-finite J gives e = 0. A singular J does not throw. LU records the first zero pivot in info, QR the first zero diagonal entry of R, LDLᵀ the first zero pivot block (or 1 for a non-finite entry), and returncode then gives SINGULAR. QR is not rank-revealing: a singular J whose R has no exact zero on the diagonal gives SUCCESS, and two equal rows, as a rule, give no exact zero. The SVD records its numerical rank in rank, the number of singular values above the cutoff √m · eps(TF) · σ₁, m the number of rows of J, and a rank deficiency gives info == 0 and SUCCESS; its info is nonzero only where the sweep did not converge or a singular value is not finite, and rank is then 0. The SVD is prescaled at the working precision too, because the sweep squares the entries.

For a dense or device factor (R3), fac is a DenseLU, DenseQR, DenseSVD, DenseLDLT, DeviceLU, DeviceQR, DeviceSVD or DeviceLDLT built by init_linear. J is written into fac.factors, divided by 2^e as for a static matrix where its element type is not that of fac.factors, and fac.factors is factorised in place; J === fac.factors is factorised as it is. A DenseSVD or DeviceSVD divides J by 2^e unconditionally, J === fac.factors too: into fac.factors on the host before gesvd, and into fac.U on a device before the one-sided Jacobi sweep. For DenseSVD, info is 1 where J has a non-finite entry, which is refused before gesvd and leaves U, S and VT unwritten, gesvd's non-convergence code where it fails, or 1 where a singular value of J / 2^e is not finite; for DeviceSVD it is 1 where the Jacobi sweep reaches its sweep cap without converging or meets a non-finite entry; rank is the numerical rank as for a static matrix. An Inf in a dense J does not throw; the SVD and LDLᵀ then report SINGULAR, and the step that the LU or QR factors give is not specified.

For a sparse factor (R3), which an extension builds in init_linear from a SparseMatrixCSC jacobian_prototype, J must have the sparsity pattern of that prototype, or ArgumentError is raised. A zero pivot, a non-finite entry of J and a non-finite factor give info = 1 and SINGULAR without throwing.

A precision marker such as TF32 has no method for a static matrix: the call raises a MethodError.

GeometricSolvers.ldiv!! — Function
ldiv!!(d, fac, r)

Solve A d = r with the factors fac of A, and return d in the element type of r. For a rectangular A of size m × n with m > n (the QR and SVD factors of a LeastSquaresProblem), r has m entries, d has n, and d is the least-squares solution of A d = r, the minimum-norm one where an SVD factor has numerical rank below n.

For a static factor (R1), d is nothing and the result is a new SVector. For a dense factor (R3), d is the vector buffer written in place and returned. Where the element type of r is the element type of the factors, the solve runs directly in it. There a finite, nonzero r whose largest |re| or |im| is within a few bits of floatmax (2 + ⌈log2 N⌉ bits for N entries) is divided by the smallest power of two 2^k that leaves that headroom; any other r is solved as it is. This keeps Qᴴ r and Uᴴ r, which the QR and SVD solves form first, finite. The SVD, whose factors are those of J / 2^e, then divides the coordinates Uᴴ r by its singular values times the smallest power of two 2^t that keeps the coordinates the same headroom below floatmax; t is 0 wherever they are already below it, and for LU and QR. The step is multiplied by 2^(k + t - e), in one rounding, with e the exponent of factorize!!, so that the SVD step does not overflow where it is representable. The LU and QR solves can still overflow in the triangular solve for such an r. An entry of r within k bits of the subnormal range can lose those bits to the division, and a coordinate within t bits of it to the SVD's. The step still overflows on every route where the solution itself exceeds floatmax. Where the element types differ, a finite, nonzero r is scaled by s = maximum(abs, r), converted to the factor type, solved, converted back and multiplied by s (Kelley 2023, eqs. 2.17–2.18). Normalisation prevents overflow from the overall right-hand-side scale in a lower factor precision; entries small relative to the largest entry can still underflow. The scale takes no squares and overflows only where an entry's absolute value does. In the mixed-type path, a zero r returns a zero step without solving, and an Inf or NaN in r gives a non-finite step. In both paths the step is multiplied by 2^-e, the power of two that factorize!! divided J by, in the element type of r. The SVD's solve leaves out the directions that its rank cutoff counted as zero, so that a rank-deficient system gives a finite, truncated step rather than an enormous one; an SVD factor with info ≠ 0 has rank 0 and gives the zero step.

Matrix-free Krylov solves

GMRES is a LinearMethod with no factor. The Jacobian enters a step only through a Jacobian–vector product, so a Newton with it holds no n × n Jacobian (state.J === nothing) and serves a system that no array can hold the Jacobian of: a small system whose every column costs a full evaluation of an expensive residual, or a device array. Its step solves $J M^{-1} u = -F(x)$ and returns $d = M^{-1} u$ to the relative tolerance that the forcing term returns.

The forcing term sets that tolerance. EisenstatWalkerChoice2 is the default, and EisenstatWalkerChoice1 and FixedForcing are the alternatives; a term is an AbstractForcingTerm, and compute_forcing is its rule. The right preconditioner of GMRES(; preconditioner = P) is refreshed by refresh! once per Newton step and applied by apply_preconditioner! before every product. A matrix-free problem supplies its own product as JVPFunction(jvp!) in the jacobian field of Newton, and the solve reports the exact counts of its residual and product evaluations in f_calls/jvp_calls and in the f_calls and jvp_calls fields of SolverStatus. A combinator other than Repeat reports 0 in those fields, because its members count only their own steps. GMRES(; maxiter) caps the inner iterations of one Newton step, and max_inner_iterations gives the largest count of the last solve.

The matrix-free DogLeg runs on the Arnoldi relation of an unrestarted GMRES only (restart == maxiter), and a Newton with a preconditioner or a restarted GMRES under it raises an ArgumentError. These names are exported.

GeometricSolvers.GMRES — Type
GMRES(; maxiter = 30, restart = nothing, forcing = EisenstatWalkerChoice2(),
        preconditioner = nothing, jvp_eltype = Nothing)

The R5 matrix-free Newton–Krylov linear solver of Newton: right-preconditioned GMRES with modified Gram–Schmidt on the Jacobian–vector product of the problem, the forcing term forcing (EisenstatWalkerChoice2 by default, EisenstatWalkerChoice1 or FixedForcing), a right preconditioner preconditioner, and the element type jvp_eltype of the product.

Fields

  • maxiter::Int32: the cap on the inner GMRES iterations of one Newton step, ≥ 1. Under a DogLeg the cap is min(maxiter, n), one Arnoldi cycle, because its model reads the Arnoldi relation of that cycle. A step that reaches the cap without meeting the tolerance of its forcing term counts a step-rule failure.
  • restart::Int32: the number of inner iterations between restarts, 1 ≤ restart ≤ maxiter. restart = nothing stores maxiter, which is unrestarted GMRES, and which DogLeg needs. The Krylov basis holds min(restart, n) + 1 columns.
  • forcing::F: the rule that sets the relative tolerance $\eta_k$ of step k.
  • preconditioner::P: the right preconditioner, nothing for none. refresh!(P, prob, x, Fx, p) is called once per Newton step, before GMRES starts, and apply_preconditioner!(z, P, v) once per inner iteration; the solve forms $J M^{-1} u = -F$ and returns $d = M^{-1} u$. A type that carries a preconditioner extends those two functions, for example a stored factorisation that ldiv! applies, which is the frozen-Jacobian preconditioner of a Newton–Krylov method.
  • jvp_eltype::Type{TJ}: Nothing evaluates the Jacobian–vector product in the working type of the iterate; a real type TJ evaluates it in TJ and promotes the product to the working type, which is a defect-correction solve: a product in a lower precision, a residual in the working one. The iterate, the residual and every norm stay in the working type.

A Newton with GMRES allocates no n × n Jacobian, and its iterate must be an AbstractVector: a Number and a StaticArray have no Krylov basis here, and a LeastSquaresProblem has no square system. The solve calls no Jacobian function of the problem: the product comes from the jacobian of the Newton, a JVPFunction or an AD back end, AutoForwardDiff() by default. A residual that the back end cannot differentiate therefore needs a JVPFunction, even where the problem carries a Jacobian. For the same reason solve refuses a ForwardDiff.Dual in x₀ or p for a Newton with GMRES with an ArgumentError, before the solve: implicit differentiation factorises the Jacobian at the root. A constructor refuses maxiter < 1 and a restart outside 1:maxiter with an ArgumentError, and so does a Newton with a DogLeg globalization and a preconditioner or a restart < maxiter; a kernel cannot format a message, so each message is constant.

\[\eta_k^{\mathrm{raw}} = \gamma \Bigl(\frac{\|F_k\|}{\|F_{k-1}\|}\Bigr)^{\alpha}, \qquad \eta_k = \max\Bigl(\min\bigl(\eta_k^{\mathrm{safe}}, \eta_{\max}\bigr), 2\varepsilon(R)\Bigr),\]

Eigensolver

jacobi_eigen is a function on a matrix and not a linear-solver method: cyclic two-sided Jacobi for a Hermitian or a real symmetric matrix, on the rotations and the round-robin ordering of the Jacobi SVD with a Frobenius-norm pair floor eps(R) * ‖H‖_F, for the case jacobi_eigen(im * M) of a real skew M that the ProjectedSkew exponential algorithm of GeometricOptimizers needs. It adds no method to LinearAlgebra.eigen, because a method of eigen for a StaticArrays type would be type piracy.

GeometricSolvers.jacobi_eigen — Function
jacobi_eigen(A)

The eigenvalues and the eigenvectors of the Hermitian matrix A, or of a real symmetric one, by cyclic two-sided Jacobi: the rotations and the round-robin ordering of the Jacobi SVD of SVDFactorization, applied to the rows and the columns of A at once. The eigenvectors are unitary to working precision, which is what the ProjectedSkew exponential algorithm of GeometricOptimizers needs of them. A pair whose off-diagonal entry is at or below eps(real(eltype(A))) * ‖A‖_F is skipped, which is what ends the sweep on a rank-deficient or low-rank matrix, as the SVD's negligible-column guard ends its own.

The call returns (values, vectors, status): values holds the N eigenvalues in real(eltype(A)), vectors the columns of the unitary V with A = V * Diagonal(values) * V', and status is SUCCESS where the sweep reached its fixed point, or MAXITERS where it reached its cap of 30 sweeps first. All three are isbits, so the call runs inside a kernel.

The matrix is assumed Hermitian: the call reads its lower triangle and sets the upper triangle to the conjugate of the lower one on entry, so a matrix that is not Hermitian gives the eigensystem of that Hermitian part and not the one of A. A NaN or an Inf entry is not checked: nothing throws, and the sweep reaches its cap for N ≥ 2; at N = 1 there is no pair, so the call returns SUCCESS.

For a real skew matrix M, the Hermitian matrix is im * M, with the eigenvalues values of im * M and

exp(M) ≈ real(V * Diagonal(exp.(-im .* values)) * V')

to working precision — the ProjectedSkew case, which is what jacobi_eigen exists for.

GeometricSolvers.Backtracking — Type
Backtracking(; c₁ = 1e-4, p = 0.5, maxiter = 100)

The Armijo line search with a safeguarded quadratic and cubic interpolation step. It shrinks the trial step until the sufficient_decrease test

\[φ(α) - φ(0) ≤ \min\bigl(0,\ c_1 α φ′(0) + τ\bigr)\]

holds, where $τ$ is the roundoff of $φ(0)$. Each backtrack takes the minimiser of the model through $φ(0)$, $φ′(0)$ and the last one or two trials, clamped to $[0.1 α, p α]$. A trial whose merit is not finite gives no model; the next trial is then the smaller of $0.1 α$ and the geometric mean of $α$ and the step floor. The search stops at the step floor smallest_step, after two trials at steps below $\sqrt{\mathrm{eps}}$ whose merit equals $φ(0)$ bit for bit, or after maxiter trials.

The slope $φ′(0)$ comes from the step kind: $-2φ(0)$ for an ExactStep, one evaluation for a MeasuredSlope, the number itself for a slope passed in. For an InexactStep with residual $η$ the test is Eisenstat and Walker's $\|r(x + α d)\| ≤ [1 - c_1 (1 - η(α))] \|r\|$ with $η(α) = |1 - α| + α η$, and the model slope is $-2(1 - η) φ(0)$.

The model is built from differences of the merit divided by $|φ′(0)|$, and the cubic step uses the form that does not cancel on a near-quadratic merit, so the trials do not depend on the scale of the merit.

GeometricSolvers.Bisection — Type
Bisection(; αmax = 65536.0, maxiter = 100)

The line search that bisects $φ′$ for a minimiser of the merit along the line. It brackets from the anchor: the lower end starts at $0$, where $φ′(0) < 0$, and the upper end at the trial step, doubled while $φ′ < 0$, up to the smaller of its own αmax and the caller's. So the bracket always holds a sign change from $-$ to $+$: a minimum, never a maximum. A $φ′$ that is not finite counts as not descending, so the bracket never grows into a region where the merit is not finite.

It then bisects the bracket. While the bracket spans more than a factor 2, the next trial is the geometric mean of its ends, with a lower end of $0$ taken as the step floor smallest_step; after that it is the middle. It stops when the width is below $\sqrt{\mathrm{eps}}$ times the upper end, or when the lower end is still $0$ and the upper end is within a factor 2 of the floor. So the number of trials grows only with $\log_2 \log_2$ of the ratio of the trial step to the floor, and it stays bounded for αmax = Inf. While the lower end stays at $0$, a search from the trial step $α$ costs at most $3 + ⌈\log_2 \log_2(α / \mathrm{floatmin}(R))⌉$ evaluations, because the floor is at least floatmin(R): 10 in Float32 and 13 in Float64 for $α = 1$.

It returns the lower end of the bracket, where $φ′$ is finite and negative, its upper end if the lower end is $0$, or the ceiling if $φ′$ is still negative there, and classifies it by the merit there: one evaluation of $φ$ after one $φ′$ per trial.

GeometricSolvers.StrongWolfe — Type
StrongWolfe(; c₁ = 1e-4, c₂ = 0.9, αmax = 65536.0, maxiter = 100)

The line search for a step with the strong Wolfe conditions

\[φ(α) - φ(0) ≤ c_1 α φ′(0), \qquad |φ′(α)| ≤ c_2 |φ′(0)|,\]

$0 < c_1 < c_2 < 1$: Nocedal and Wright's Algorithms 3.5 and 3.6. The first condition is the sufficient_decrease test without a round-off allowance. The bracketing phase doubles the trial step up to the smaller of αmax and the caller's ceiling until a trial fails the first condition, does not decrease the merit, or has $φ′ ≥ 0$. The zoom phase then takes the minimiser of the cubic through the merit and its derivative at both ends of the bracket, or of the quadratic through both merits and the derivative at the lower end where the upper end has no derivative. The trial is safeguarded to the inner 80 % of the bracket, and it is the middle after a trial that shrinks the bracket by less than a factor 0.66, as in Moré and Thuente. The lower end is the trial with the lowest merit that meets the first condition, up to the roundoff of the larger of two merits: a trial within it of the lower end ties with it, and the sign of $φ′$ at the trial decides the side of the minimiser. A zoom trial that meets both conditions is accepted whatever its merit.

$φ′$ is evaluated only at a trial that meets the first condition and, in the bracketing phase, decreases the merit: a trial that fails costs one $φ$, a trial that passes one $φ$ and one $φ′$.

It returns SUCCESS only for a step that meets both conditions and decreases the merit by more than its round-off. Every other search returns its lowest trial that meets the first condition, or else its last trial. At the ceiling, at a collapsed bracket or at the step floor smallest_step the code is STALLED if the merit is at its round-off floor and LINESEARCH_FAILED otherwise; after maxiter trials it is LINESEARCH_FAILED.

GeometricSolvers.DogLeg — Type
DogLeg(; radius = nothing)

The trust-region globalization of Newton on the dogleg curve: Newton(; globalization = DogLeg()). It is not a LineSearch: it needs the Jacobian, its factor and a radius that lives from one iteration to the next, so Newton holds the radius in its state and runs the trial loop with its own Jacobian.

The defaults are Procedure 4.1 of Pawlowski, Simonis, Walker and Shadid (2008). The step is the Newton step when it lies in the radius $δ$, else the Cauchy step along $-J^* F$ scaled to $δ$ when the Cauchy point lies outside $δ$, else the point of norm $δ$ on the segment from the Cauchy point to the Newton step. $J$ is the matrix that was factorised, regularisation included. A trial is accepted when the predicted reduction $\mathrm{pred} = \|F(x)\| - \|F(x) + J s\|$ is positive and the actual reduction $\mathrm{ared} = \|F(x)\| - \|F(x + s)\|$ satisfies $\mathrm{ared} ≥ 10^{-4} \mathrm{pred}$, with unsquared norms; a rejected trial shrinks $δ$ to $\max(δ/4, 10^{-6})$ and chooses again on the same curve, with no new Jacobian or solve. So a rejected Newton step that lies well inside $δ$ is tried again, at one evaluation of F each time, until $δ$ falls below its norm. A rejection at $δ = 10^{-6}$ returns LINESEARCH_FAILED with the iterate kept. After an accepted step with ratio $ρ = \mathrm{ared} / \mathrm{pred}$, $ρ < 0.1$ sets $δ$ to $\max(\|s^{N}\|, 10^{-6})$ when the Newton step $s^{N}$ is shorter than $δ$ and to $\max(δ/4, 10^{-6})$ otherwise, and $ρ > 0.75$ on the boundary sets it to $\min(4δ, 10^{10})$. An accepted step other than the whole Newton step sets limited in its StepInfo: the radius or the Cauchy point, not the distance to a root, sets its norm, so the solve applies only the residual test after it.

radius is the initial radius. It must be positive and finite as given; DogLeg stores it converted to float(typeof(radius)), and ToReal to the iterate's real type, clamped to $[10^{-6}, 10^{10}]$ after each conversion. With nothing, the first step starts the radius at the norm of the first Newton step, clamped the same way, except that a norm below $10^{-6}$ starts it at $2 \cdot 10^{-6}$, as Procedure 4.1 does. A failed factor, or a Newton step whose norm is zero or not finite, gives no Newton step: the step is then the Cauchy point, cut to the radius when it lies outside, and a first radius starts at the length of the Cauchy point, by the same rule. The Cauchy direction is formed from the unit residual, $\tilde g = J^* F / \|F\|$, so no norm of $J^* F$ occurs, and a common scale of $F$ and $J$ leaves the Cauchy point unchanged up to rounding, as long as the norm of $\tilde g$ is finite. Where the Cauchy point is needed and $\tilde g$ is zero or its norm is not finite, or $J \tilde g / \|\tilde g\|$ is zero or its norm is not finite, the step returns STALLED with the iterate kept. At $F(x) = 0$ the step returns SUCCESS with the iterate and the radius kept, and makes no trial.

DogLeg takes no factor reuse: Newton(; globalization = DogLeg(), reuse = k) raises an ArgumentError.

GeometricSolvers.LevenbergMarquardt — Type
LevenbergMarquardt{R, S}
LevenbergMarquardt(::Type{R} = Float64; μ₀ = R(1e-6), μ_min = max(R(1e-15), 4 * eps(R)),

Adaptive Levenberg–Marquardt damping for Newton, computing the trial step from the damped linear model (J(x)ᴴ J(x) + μ Dᵀ D) δ = -J(x)ᴴ F(x) with damping parameter μ > 0 adapted from the gain ratio

\[\rho = \frac{\|F(x)\|_2^2 - \|F(x + \delta)\|_2^2}{\|F(x)\|_2^2 - \|F(x) + J(x)\,\delta\|_2^2}.\]

μ is absolute, in the units of J(x)ᴴ J(x): scaling the residual by k scales J(x)ᴴ J(x) by k² and leaves μ as it is, so a damping of μ on k J(x) acts as μ / k² does on J(x), and the μ → 0 limit is the Newton step, truncated to the numerical rank as the solve of SVDFactorization truncates it, whatever the scale. With scaling = :diagonal, D is instead the diagonal of the column norms of J(x), floored at √eps of the largest of them.

With SVDFactorization and scaling = :none, J(x) = U Σ Vᴴ is factorised once per outer step and each trial μ evaluates the damped pseudoinverse step from (U, Σ, V) without refactoring J(x). With QRFactorization, LUFactorization or LDLTFactorization (or when scaling = :diagonal), [J(x) | -F(x)] is reduced once per outer step to an upper-triangular (R₀, c₀) and each trial μ copies that pair and eliminates only its own damping rows √μ D by Givens rotations, without forming J(x)ᴴ J(x); for a LeastSquaresProblem the rows of J(x) past its n columns are eliminated into the same n × n pair. This reduction reads no symmetry, so it serves the Hessian of a StationarityProblem as any other J(x). That path indexes scalars and runs on a host array: an init on a device array iterate raises an ArgumentError for it. Neither path reads a sparse factor, so an init on a non-static array iterate whose problem carries a sparse jacobian_prototype raises an ArgumentError too. A μ below 4 eps of the working type, which only an initial μ₀ below the schedule's floor can be, is taken as no damping: the truncated Newton step, the μ → 0 limit.

A solve starts at μ₀. A trial is accepted when ρ > ρ_accept, and an accepted step sets μ to max(μ · μ_decrease, max(μ_min, 4 eps(R))). A rejected trial, or one whose step is not finite, sets μ to max(μ · μ_increase, max(μ_min, 4 eps(R))) and solves again within the same step, with no new Jacobian, until a trial is accepted or μ > μ_max, which returns STALLED with the iterate kept. A step accepted at a μ above μ₀ sets limited in its StepInfo. The parameters satisfy 0 < μ_min ≤ μ₀ ≤ μ_max < Inf, 0 < μ_decrease < 1 < μ_increase, 0 ≤ ρ_accept < 1 and scaling ∈ (:none, :diagonal), else the constructor raises an ArgumentError; ToReal converts them to the real type of the iterate. Newton(; globalization = LevenbergMarquardt(), reuse = k) raises an ArgumentError.

A nonlinear solver holds its algorithmic configuration (linsolve, globalization, jacobian, refinement, regularization and reuse for Newton; damping and globalization for Picard) and nothing about the problem or the iterate. Mixed-precision refinement

A Newton step whose factorisation runs in a precision TF below the working precision T of the iterate — linsolve = LUFactorization(Float32) on a Float64 problem — corrects its linear direction in T. Refinement is the LU-IR loop of Kelley 2023: the factor's TF solve, the residual -F(x) - J d in T, and the correction that solve gives, to the tolerance max(η, √eps(T)) ‖F(x)‖. GMRESRefinement adds the SDD variant of Amestoy et al. 2024 in front of the refactorisation of the Jacobian in T: where the LU-IR passes fail, a left-preconditioned GMRES in T solves for a correction with a copy of the same Float32 factors promoted to T, so the step reaches the accuracy of a factorisation in T without forming one. The remedy chain of a step is therefore LU-IR -> GMRES-IR -> refactorisation in T, and SolverStatus counts each failed stage in step_failures and records a factorisation in T in promoted.

The buffers of a mixed-precision solve are readable after it: stored_factors is the packed L and U of the factorisation in TF, promoted_factors the working-precision copy of it that the GMRES-IR stage promotes (or the factors of the refactorisation, where the step promoted), preconditioned_buffer the slot of the preconditioned product the inner GMRES forms, and linear_residual_buffer the slot of the linear residual -F(x) - J d. scripts/gmres_ir_comparison.jl runs both methods at κ∞ ∈ {1e4, 5e7, 2e8, 5e10}, prints their Newton iteration counts and linear residuals, and recomputes both from the raw output of the solves.

Combinators

Additive, Multiplicative, Repeat, Switch, Anderson and Broyden compose nonlinear methods through the same init_state, start!!, step!! and finish!! interface as Newton and Picard, so a combinator runs in R1, R2 and R3 alike. Additive combines member steps from the same iterate with OptimalWeights or FixedWeights, Multiplicative and Repeat thread (x, F(x)) sequentially across sub-steps while sync_merit updates any active line-search baseline merit, Switch transitions permanently from first to second once $\|F(x)\| \le \text{threshold} \cdot \|F(x_0)\|$, Anderson accelerates its member with filtered Type-II Anderson mixing, Tikhonov regularisation, restarts and best-iterate restoration, and Broyden accelerates its member over the same shared AndersonHistory, filters and safeguards by solving the lower-triangular Type-II Broyden multisecant equations by forward substitution. A combinator has no implicit differentiation: solve with a combinator method raises an ArgumentError for a ForwardDiff.Dual in x₀ or p.

Nonlinear preconditioning

LeftPreconditioned(outer, inner) runs outer on the residual $r^\ell(y) = y - N(y)$ of one step of inner instead of on F, so every trial point of its globalization costs one inner step and every merit value it reads is $\|r^\ell\|_2^2$. With the inner method a one-level RAS map over a BlockPartition it is RASPEN, LeftPreconditioned(Newton(), RAS(partition)), whose Jacobian is the exact form from the block factors of the last sweep; RASPEN needs converged local solves. Multiplicative(RAS(partition), Newton()) is NKS-RAS, the same map followed by one Newton step. A RAS sweep restricts each subdomain, solves each block with the package's own factor, and prolongates through the owner sets only, so each index of 1:n is written once and the sweep calls the global residual no times; ras_counts reports the counters of its last solve. A problem with block residuals supplies the block functions, and a block without a Jacobian is differentiated by AutoForwardDiff().

LeftPreconditioned(outer, inner)

The left-preconditioned method of a NonlinearProblem: the method outer runs on the residual $r^\ell(y) = y - N(y)$ of the inner map $N$, one step!! of inner from (y, F(y)), instead of on F itself. Every trial point of outer's globalization therefore costs one inner step, and every merit value it reads is $\|r^\ell\|_2^2$. The zeros of $r^\ell$ are the fixed points of $N$.

LeftPreconditioned(Newton(), RAS(partition)) is RASPEN: the merit is on the restricted additive Schwarz map, and the Jacobian of $r^\ell$ is the exact form of raspen_jvp! built from the block factors of the last sweep (Dolean:2016, eq. 3.17). RASPEN needs converged local solves: a RAS with a positive tolerance whose local solve does not converge returns MAXITERS, and a LeftPreconditioned step that meets it, at its iterate or at the trial point where its outer step reports NONFINITE, returns MAXITERS too, which ends the solve. A Newton with GMRES as outer is refused at init_state with an ArgumentError, because it solves a NonlinearProblem and outer solves $r^\ell$; as inner it is taken. outer may be a combinator, such as Repeat or Multiplicative, whose members step on $r^\ell$; with a RAS inner, every member of an Additive after the first costs one more sweep, at the iterate, because the RASPEN Jacobian reads the block factors of the last sweep. SciMLBase extension

When SciMLBase is loaded, the package extension GeometricSolversSciMLBaseExt adds methods of solve and init for a SciMLBase.NonlinearProblem and a method Newton or Picard. Both translate the problem and call the native solve or init, so solve returns (x, status), init returns a NonlinearSolver that holds a copy of an array u0, and solve!(init(prob, method; kwargs...)) returns what solve(prob, method; kwargs...) returns; the native solve! serves the solver. A SciML caller maps status.code to a SciMLBase.ReturnCode.T with sciml_retcode (GeometricSolvers.sciml_retcode(status.code)), which is public and not exported.

The call form follows SciMLBase.isinplace(prob) and u0 = prob.u0: an out-of-place f(u, p) with a StaticArray or a Number u0 solves in R1 and returns a value of the type of u0 (with an SVector u0, an out-of-place jac(u, p) must return an SMatrix, as the native R1 J does); an in-place f(du, u, p) with an array u0 that is not a StaticArray solves in R3 on a copy of u0; an out-of-place f(u, p) with such an array u0 solves in R3 through a closure wrapper (y, x, p) -> (y .= f(x, p)) (and (A, x, p) -> (A .= jac(x, p)) for prob.f.jac), which allocates as f and jac do; and an in-place f with a StaticArray or a Number u0 raises an ArgumentError. prob.f.jac becomes the J of the native problem (overridden by a method's own jacobian field), and prob.p is passed unchanged, SciMLBase.NullParameters() included. A problem with jac_prototype, sparsity, lb or ub set raises an ArgumentError.

The extension merges prob.kwargs with the call's keywords (the call's winning) and accepts the closed set abstol, reltol, maxiters and options: abstol maps to f_abstol (and sets f_reltol = 0 when reltol is not given), reltol maps to f_reltol, maxiters maps to max_iterations, and options passes an Options alone; any other keyword, or options together with another keyword, raises an ArgumentError.

Automatic differentiation

In R1, prepare_ad returns the AutoForwardDiff() back end itself for a StaticVector or a Number iterate. jacobian!!, gradient_hessian!! and jvp!! run tagged ForwardDiff directly with that source. The source nothing calls the problem's own J; a JacobianFunction calls a method's operator for jacobian!! only. A back end other than AutoForwardDiff has no R1 method, and the call is a host MethodError.

In R3 the AD path is chosen once, by prepare_ad, from the back end and the storage of the iterate: AutoForwardDiff() goes through an own chunked forward mode on every array type (ChunkedForwardDiff for NonlinearProblem and ChunkedHessianForwardDiff for StationarityProblem), and any other back end goes through DifferentiationInterface on a CPU iterate (DIJacobian and DIStationarity), so every ADTypes back end works with no line of source here. A device array iterate takes AutoForwardDiff() only, because DifferentiationInterface's jacobian! raises a scalar-indexing error on an MtlArray, a CuArray and a JLArray. When the problem supplies an analytic 3-argument J(Jbuf, x, p), JacobianMatrixJVP evaluates prob.J into its pre-allocated matrix buffer and multiplies by the direction in place. Only a LineSearch other than Static and a Refinement along a reused factor take a JVP, so under any other configuration the analytic J gets no JVP preparation and no second m × n buffer. A Refinement on a step that factorises at x multiplies by the regularised Jacobian that the step holds, in a buffer of its own beside the factor, which the factorisation overwrites. jacobian!!, gradient_hessian!! and jvp!! then dispatch on the object the preparation returned, so the solver makes no runtime choice and carries no ad keyword.

For a sparse R3 Jacobian on a host Array iterate, an AutoSparse back end takes either an explicit jacobian_prototype on the NonlinearProblem (which prepare_ad wraps in KnownJacobianSparsityDetector) or, when SparseMatrixColorings is loaded and jacobian_prototype === nothing, a sparsity detector such as TracerSparsityDetector() of SparseConnectivityTracer alongside a colouring algorithm such as GreedyColoringAlgorithm(). The GeometricSolversSparseADExt package extension then extracts the detected pattern from the prepared DIJacobian via jacobian_pattern as a SparseMatrixCSC{<:Any, Int} — a SparseMatrixCSC{Bool, Int} for TracerSparsityDetector — so init_linear allocates the sparse factor and Jacobian buffer without a user-supplied prototype where has_sparse_factor holds, and the dense factor elsewhere; when an explicit jacobian_prototype is also given, the explicit prototype takes precedence.

In R3 the iterate is a vector; another shape raises ArgumentError where the preparation is built. The parameters may be replaced on every call, which is what lets one preparation serve a whole time-stepping loop.

AutoEnzyme reaches the Array path through DifferentiationInterface like any other back end, but it needs runtime activity for the parameter context — AutoEnzyme(; mode = Enzyme.set_runtime_activity(Enzyme.Forward)). A plain AutoEnzyme() raises EnzymeRuntimeActivityError on a residual that broadcasts constant parameters into its result; see KNOWN_ISSUES.md. The mode is the caller's choice, so the package sets none.

GeometricSolvers.LineSearch — Type
LineSearch{R}

The supertype of the line searches Static, Backtracking, Bisection and StrongWolfe, whose numbers are of the real type R. A line search is a method: it is isbits, it holds numbers and, except Static, an Int32 cap and nothing else, and linesearch runs it.

Every line search keeps six contracts:

  1. It never throws. A constructor checks its parameters on the host and raises an ArgumentError; linesearch raises nothing.
  2. It returns $α > 0$.
  3. It reports through the code of its LineSearchResult and never logs.
  4. A non-finite or ascending anchor is reported, not searched: NONFINITE and LINESEARCH_FAILED. A stationary anchor, $φ′(0) = 0$, is STALLED. Static is the exception: it reads no anchor and returns its step.
  5. Its number of evaluations does not depend on the scale of the merit.
  6. It returns $α ≤ α_{max}$, for the caller's αmax and for its own.

It never evaluates the merit at $α = 0$: the caller passes $φ(0)$, which is the residual it already has.

GeometricSolvers.InexactStep — Type
InexactStep(η)

The step kind of a direction d with the linear residual $\|r + J d\| ≤ η \|r\|$, $0 ≤ η < 1$. It gives only $φ′(0) ≤ -2(1 - η) φ(0)$ (Eisenstat and Walker 1996, (1.2)). Along $α d$ the linear residual is $(1 - α) r + α (r + J d)$, so its bound is $η(α) = |1 - α| + α η$. Backtracking tests $\|r(x + α d)\| ≤ [1 - c_1 (1 - η(α))] \|r\|$ with this $η(α)$, which for $α ≤ 1$ is the update $η ← 1 - θ (1 - η)$ of each backtrack by $θ$, and evaluates no $φ′$. A step with $η(α) ≥ 1$ promises no decrease and is rejected. Bisection and StrongWolfe need the true slope and evaluate $φ′(0)$. The constructor checks nothing, so that solver code can build one in a kernel: a search given an $η$ outside $[0, 1)$ evaluates nothing and returns LINESEARCH_FAILED. Static reads no step kind and returns its step.

  • code::ReturnCode: SUCCESS for an accepted step that decreases the merit by more than its round-off, and for the step of Static, which evaluates nothing; STALLED for a step that changes the merit by no more than its round-off, or a stationary anchor; NONFINITE for a non-finite anchor; LINESEARCH_FAILED for anything else: an ascending anchor, a spent cap, an increase of the merit, an invalid αmax, or a StrongWolfe step without the curvature condition. φ tells the caller whether the step of a failure still decreases the merit.
  • evaluations::Int32: the evaluations of φ and φ′ together. A StrongWolfe search whose trials share one residual buffer evaluates F once more at a result step that is not its last trial, to restore residual; that evaluation is not counted.
  • residual::Q: the residual at α that gave φ; the residual at $α = 0$ where φ is NaN; nothing for a line function with no residual.

GeometricSolvers.roundoff — Function
roundoff(φ₀)

The round-off resolution $τ = 4\,\mathrm{eps}(R)\,|φ(0)|$ of the merit, four units of relative round-off. A step that changes the merit by no more than $τ$ is at the round-off floor of the merit. It is proportional to $|φ(0)|$, not a count of ulps of $φ(0)$, so that it and the step floor smallest_step scale with the merit and do not jump by a factor 2 at a power of two. For a subnormal $φ(0)$, where the product underflows, it is at least four of the smallest subnormals, so it is never 0.

GeometricSolvers.sufficient_decrease — Function
sufficient_decrease(φα, φ₀, demand, τ)

The Armijo test on the difference, $φ(α) - φ(0) ≤ \min(0, \mathrm{demand} + τ)$, where demand is the negative decrease the test demands and $τ$ the round-off allowance. The difference keeps a demand below one ulp of $φ(0)$, which $φ(0) + \mathrm{demand}$ would round away; the min lets $τ$ lower the demand, never accept an increase. StrongWolfe passes $τ = 0$.

GeometricSolvers.backtrack_step — Function
backtrack_step(φ₀, d₀, α, φα, αp, φp, p)

The next trial step after the rejected trial α with merit φα; αp and φp are the trial before it, and αp is NaN on the first backtrack. The model of $φ$ is a quadratic through $φ(0)$, $φ′(0) = d_0$ and $φ(α)$, then a cubic through $φ(α_p)$ as well, both in the merit divided by $|d_0|$. The cubic minimiser is $1 / (b + \sqrt{b^2 + 3a})$ for $b > 0$, which does not cancel as $a → 0$. The result is clamped to $[0.1 α, p α]$; a model without a minimiser gives $p α$, and a merit that is not finite at α gives $0.1 α$.

GeometricSolvers.zoom_step — Function
zoom_step(a, φa, da, b, φb, db)

The minimiser of the cubic through the merit φa, φb and its derivative da, db at the two ends a and b of a bracket (Nocedal and Wright, (3.59)), clamped to the inner 80 % of the bracket. The discriminant is scaled by the largest of $|θ|$, $|d_a|$, $|d_b|$, as in Moré and Thuente, so it neither overflows nor depends on the scale of the merit. A cubic without a minimiser gives the middle of the bracket. Without a finite db it is the minimiser of the quadratic through φa, da and φb.

GeometricSolvers.gmres_solve! — Function
gmres_solve!(ws::GMRESWorkspace, jvp_op!, P, b, bnorm, tol, maxiter, restart)
    -> (d, GMRESInfo)

Solve J d = b with right-preconditioned GMRES in the workspace ws, and return the direction d = M⁻¹ u in the slot ws.d and a GMRESInfo. jvp_op!(Jv, v) writes the product J v into Jv; P is the right preconditioner; b is the right-hand side and bnorm its norm $\|b\|_2$, which the caller already holds; tol is the relative tolerance, so that the solve stops at $\|b - J d\|_2 \le tol \cdot bnorm$; maxiter caps the inner iterations and restart the iterations between restarts, neither of which may exceed the width the workspace was allocated for.

The Arnoldi process is modified Gram–Schmidt with the conjugated inner product, so a complex iterate is supported and every norm is in real(T). A zero H[j+1, j] is a breakdown: the Krylov space is invariant, and the solve stops there rather than dividing by zero. The residual of the reduced problem is then zero, unless J is singular on that space: the rotated diagonal entry is then zero too, the residual is that of the last entry of the right-hand side, and the solve reports no convergence. A restarted cycle forms its new residual with one more product, b - J M⁻¹ u, so a restart costs one Jacobian–vector product. The least-squares problem is solved from the Givens-rotated Hessenberg matrix, whose diagonal entry is 0 only where the reduced system is singular, and the corresponding weight is then 0.

gmres_ir!!(d, ref, state, fac, J, Fx, fnorm) -> (d_ir, ok, ran, linrel, state)

Stage 2 of the mixed-precision remedy chain of a Newton step, GMRES-IR after the LU-IR passes of d have failed: a left-preconditioned GMRES in the working precision T on $\hat{U}^{-1}\hat{L}^{-1}P J \,\delta d = \hat{U}^{-1}\hat{L}^{-1}P r_{\mathrm{lu}}$, with the copy of the factors in TF that promote_lu_factors! writes into the working-precision factor slot, a cap of min(ref.gmres_maxiter, n) inner iterations, and the tolerance ref.gmres_tol on the true linear residual $r_{\mathrm{true}} = -F(x) - J (d + \delta d)$ recomputed in T, which the stage accepts up to ten times its tolerance (Amestoy et al. 2024, p. 13; Kelley 2023, p. 7).

d is the direction the LU-IR passes reached, fac the factorisation in TF they solved with, J the regularised Jacobian the step holds in T, and fnorm the norm $\|F(x)\|$ the tolerance is relative to. It returns the direction (the GMRES-IR one where ok, else d), whether the stage met its bound, whether it ran at all (it does not where the solve keeps no working-precision factor slot and no Krylov basis, where the factor is no LU factorisation, and for any refinement that is not a GMRESRefinement), the relative true residual of the direction it returned, and the state that carries the promoted factor slot it wrote.

GeometricSolvers.rnorm — Function
rnorm(a)

The Euclidean norm $\sqrt{\sum_i |a_i|^2}$ in real(eltype(a)).

Where norm2(a) is finite and at least length(a) * floatmin(R), it is sqrt(norm2(a)), one reduction. Otherwise it scales the entries by $2^{-e}$, where $2^e$ is the power of two of the largest $|a_i|$ (of the largest real or imaginary part for a complex a), so that it neither overflows where the norm is finite nor underflows to zero where the norm is positive. That path takes two more reductions, the largest entry and the sum, and sums in at least Float32. Scaling can round the squares of entries much smaller than the largest to zero, which changes the result in the last bits at most. A NaN entry gives NaN, an Inf entry and no NaN gives Inf. Where real(eltype(a)) is no AbstractFloat, such as an integer or a ForwardDiff.Dual, it is the unscaled sqrt(norm2(a)).
