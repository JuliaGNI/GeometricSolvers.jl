Automatic differentiation

In R1, prepare_ad returns the AutoForwardDiff() back end itself for a StaticVector or a Number iterate. jacobian!!, gradient_hessian!! and jvp!! run tagged ForwardDiff directly with that source. The source nothing calls the problem's own J; a JacobianFunction calls a method's operator for jacobian!! only. A back end other than AutoForwardDiff has no R1 method, and the call is a host MethodError.

In R3 the AD path is chosen once, by prepare_ad, from the back end and the storage of the iterate: AutoForwardDiff() goes through an own chunked forward mode on every array type (ChunkedForwardDiff for NonlinearProblem and ChunkedHessianForwardDiff for StationarityProblem), and any other back end goes through DifferentiationInterface on a CPU iterate (DIJacobian and DIStationarity), so every ADTypes back end works with no line of source here. A device array iterate takes AutoForwardDiff() only, because DifferentiationInterface's jacobian! raises a scalar-indexing error on an MtlArray, a CuArray and a JLArray. When the problem supplies an analytic 3-argument J(Jbuf, x, p), JacobianMatrixJVP evaluates prob.J into its pre-allocated matrix buffer and multiplies by the direction in place. Only a LineSearch other than Static and a Refinement along a reused factor take a JVP, so under any other configuration the analytic J gets no JVP preparation and no second m × n buffer. A Refinement on a step that factorises at x multiplies by the regularised Jacobian that the step holds, in a buffer of its own beside the factor, which the factorisation overwrites. jacobian!!, gradient_hessian!! and jvp!! then dispatch on the object the preparation returned, so the solver makes no runtime choice and carries no ad keyword.

For a sparse R3 Jacobian on a host Array iterate, an AutoSparse back end takes either an explicit jacobian_prototype on the NonlinearProblem (which prepare_ad wraps in KnownJacobianSparsityDetector) or, when SparseMatrixColorings is loaded and jacobian_prototype === nothing, a sparsity detector such as TracerSparsityDetector() of SparseConnectivityTracer alongside a colouring algorithm such as GreedyColoringAlgorithm(). The GeometricSolversSparseADExt package extension then extracts the detected pattern from the prepared DIJacobian via jacobian_pattern as a SparseMatrixCSC{<:Any, Int} — a SparseMatrixCSC{Bool, Int} for TracerSparsityDetector — so init_linear allocates the sparse factor and Jacobian buffer without a user-supplied prototype where has_sparse_factor holds, and the dense factor elsewhere; when an explicit jacobian_prototype is also given, the explicit prototype takes precedence.

In R3 the iterate is a vector; another shape raises ArgumentError where the preparation is built. The parameters may be replaced on every call, which is what lets one preparation serve a whole time-stepping loop.

AutoEnzyme reaches the Array path through DifferentiationInterface like any other back end, but it needs runtime activity for the parameter context — AutoEnzyme(; mode = Enzyme.set_runtime_activity(Enzyme.Forward)). A plain AutoEnzyme() raises EnzymeRuntimeActivityError on a residual that broadcasts constant parameters into its result; see KNOWN_ISSUES.md. The mode is the caller's choice, so the package sets none.

These names are not exported. Reach them as GeometricSolvers.name.

GeometricSolvers.prepare_ad — Function
prepare_ad(backend, prob, r, x, p)

Build the AD preparation for the residual of prob at an iterate like x, with a residual buffer like r and a representative parameter set p, and return the object that jacobian!! and jvp!! dispatch on. The values of p, and the parameter object itself, may be replaced on every call.

AutoForwardDiff() gives a ChunkedForwardDiff on every array type. Any other back end gives a DIJacobian on a CPU iterate, and raises ArgumentError on a device array iterate: DifferentiationInterface's jacobian! raises "Scalar indexing is disallowed" on an MtlArray, a CuArray and a JLArray. The iterate must be a vector.

Where prob carries a jacobian_prototype, a back end other than AutoForwardDiff() raises ArgumentError unless the prototype has the size of the Jacobian, and an AutoSparse back end takes that prototype as its sparsity pattern, whatever detector it carries. AutoForwardDiff() does not read the prototype.

GeometricSolvers.prepare_jvp — Function
prepare_jvp(backend, prob, r, x, p)

Build the Jacobian–vector preparation of a solve that forms no Jacobian and reads the product alone, such as a Newton with GMRES: the same DIJacobian that prepare_ad returns, without the prepared jacobian! it would never call. AutoForwardDiff takes the own chunked forward mode of src/ad/chunked.jl on every array type; any other back end takes DifferentiationInterface's pushforward! on a CPU iterate, and raises ArgumentError on a device array iterate, as prepare_ad does. r is a residual buffer like a residual of the problem at x.

GeometricSolvers.DIJacobian — Type
DIJacobian

The AD preparation of the R3 path through DifferentiationInterface: the back end, DI's prepared jacobian! and pushforward!, and a residual buffer. prepare_ad builds it. The parameters are a context and not a differentiated argument, so each call wraps them in DI's Constant.

source
GeometricSolvers.DIStationarity — Type
DIStationarity

The R3 AD preparation for StationarityProblem with any AbstractADType back end other than AutoForwardDiff, on a CPU Array: the gradient of S gives the residual, and the (E, U) block of the Hessian of S gives the Jacobian.

The Jacobian and the Hessian-vector product are the (E, U) block of one Hessian of S, not the derivative of a gradient map: a back end of finite differences would differentiate an already finite-difference gradient, whose noise then swamps the outer difference. The Hessian is taken over the whole state, so a state far longer than the unknown set costs more here than under AutoForwardDiff(), which sweeps E × U only.

GeometricSolvers.ChunkedForwardDiff — Type
ChunkedForwardDiff{N, Tg}

The AD preparation of the R3 path of AutoForwardDiff: N Jacobian columns per residual evaluation, in one pass of ForwardDiff.Dual{Tg, T, N} arithmetic. Tg is the caller's tag, or this solver's own where the caller named none, and the same tag serves the Jacobian and the JVP.

The four fields are the dual buffers: xdual and rdual carry N partials for jacobian!!, xdual1 and rdual1 one partial for jvp!!. A complex iterate gives Complex{ForwardDiff.Dual{Tg, real(T), N}} buffers, so that a holomorphic residual is differentiated in its complex argument.

source
GeometricSolvers.ChunkedHessianForwardDiff — Type
ChunkedHessianForwardDiff{N, TgIn, TgOut}

The R3 AD preparation of AutoForwardDiff for StationarityProblem: chunked nested ForwardDiff.Dual workspaces and device-resident index maps e_pos and u_pos so that residual!!, jacobian!!, gradient_hessian!!, and jvp!! allocate zero bytes on CPU Array and perform zero scalar indexing on AbstractGPUArray.

GeometricSolvers.JacobianFunction — Type
JacobianFunction(f)

The Jacobian source of a method that carries an operator of its own: f(x, p) is that operator, and jacobian!! calls it in place of the problem's J. The method's operator is not the derivative of the residual, so it serves jacobian!! and never jvp!!.

Internal: wrap the operator in this type to pass it as the source of the R1 jacobian!! call. It holds a function and nothing else, so it is isbits exactly when that function is.

source
GeometricSolvers.JacobianMatrixJVP — Type
JacobianMatrixJVP(J)

The R3 JVP preparation when the problem provides an analytic Jacobian prob.J(J, x, p): a preallocated m × n matrix buffer J (m = n unless the problem has more residuals than unknowns) into which jvp!! evaluates prob.J(J, x, p) and multiplies by v via mul!!. Because this buffer is distinct from Newton's Jacobian buffer, evaluating a line-search slope under Jacobian reuse (reuse > 1) leaves the held Newton Jacobian untouched.

GeometricSolvers.jacobian!! — Function
jacobian!!(J, prep, prob, x, p)

The Jacobian of the residual of prob at the iterate x, for the parameters p, in the storage of J, and return it.

prep is the Jacobian source. In R1 the output slot J is nothing: nothing calls the problem's J(x, p), an AutoForwardDiff runs tagged ForwardDiff and returns an SMatrix in the element type of a vector iterate or a Number for a Number iterate, and a JacobianFunction calls the method's own function. factorize!! converts the result to the factorisation precision TF. In R3 J is an m × n buffer in the element type of x, m = n unless the problem has more residuals than unknowns: nothing calls prob.J(J, x, p), a JacobianFunction calls s.f(J, x, p), a DIJacobian runs DifferentiationInterface's prepared jacobian!, and a ChunkedForwardDiff runs the own chunked forward mode. The preparation selects the code.

GeometricSolvers.gradient_hessian!! — Function
gradient_hessian!!(F, J, prep, prob::StationarityProblem, x, p)

Evaluate both the stationarity residual F = (∇S(x, p))_E + b and its Jacobian J = (∇²S(x, p))_{E, U} at full state x and parameters p. In R1 (F === nothing and J === nothing, prep the back end AutoForwardDiff() that prepare_ad returns), one nested ForwardDiff.Dual evaluation of prob.S returns (F, J) in a single call to prob.S. In R3, F and J are written in place and returned as (F, J). The seven-argument form gradient_hessian!!(F, J, prep, backend, prob, x, p) takes prep === nothing and uses backend in R1, and uses prep and ignores backend in R3.

GeometricSolvers.jvp!! — Function
jvp!!(Jv, prep, prob, x, v, p)

The Jacobian–vector product J(x, p) * v of the residual of prob, in the storage of Jv, and return it.

With an AD source, one pushforward and exactly one evaluation of the residual make the merit derivative φ′(α) = F(x + αd)ᵀ J(x + αd) d of a line search cost one directional derivative rather than n. With the source nothing or a JacobianMatrixJVP, the call evaluates the problem's J instead of F.

prep is the JVP source from the problem, never from a method's operator, and it selects the code exactly as in jacobian!!. In R1 the output slot Jv is nothing and the call returns a new value: nothing gives J(x, p) * v from the problem's J, and an AutoForwardDiff one dual evaluation of F. The R1 direction has the element type and the length of the iterate, as the line-search slope does: a direction of another element type is a host MethodError. In R3 Jv is a buffer and prep is a JacobianMatrixJVP, a DIJacobian or a ChunkedForwardDiff.
