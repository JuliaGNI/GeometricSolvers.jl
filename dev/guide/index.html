Methods by regime

This page lists, for each regime, the methods that run in it and the conditions under which each one applies. It names no method as the right one: the choice depends on the problem, its size, the cost of its residual and its Jacobian, and the start. The pages under Algorithms describe each method in full.

The storage of the iterate selects the regime (see The three regimes). R5 is an R3 iterate with a matrix-free linear solver:

regimeiterateentry pointlinear solver
R1 value semanticsNumber or SVectorsolvea factorisation of a static matrix
R2 batchedan array of Number or SVector, one entry per systemsolve_batch!a factorisation of a static matrix, per system
R3 in placean AbstractVector that is not staticsolve, init, solve!a factorisation of a dense or sparse matrix
R5 matrix-freean AbstractVector that is not staticsolve, init, solve!GMRES, with no Jacobian matrix

Newton() takes linsolve = LUFactorization() and globalization = Static() unless the caller gives others (see Nonlinear methods).

The method of a call that names none

init(prob, x₀) and solve(prob, x₀) on a NonlinearProblem, a StationarityProblem or a LeastSquaresProblem take the method default_method(prob, x₀) and the parameters p = nothing. The method follows from the problem type, its jacobian_prototype and the storage of the iterate:

problemiteratemethod
NonlinearProblem with a SparseMatrixCSC jacobian_prototypea Vector{Float64} or a Vector{ComplexF64}Newton(; linsolve = UMFPACKFactorization())
NonlinearProblem, every other prototype and iterateany otherNewton()
StationarityProblemanyNewton()
LeastSquaresProblemanyGaussNewton()

The rules read no size. The LUFactorization() of Newton() selects its factor from the storage of the Jacobian: a static factor in R1, and on a dense array the factor that What runs where lists for its array type. A SparseMatrixCSC prototype on any other iterate takes Newton() as well: a Vector{Float32} gets the Sparspak factor where Sparspak is loaded, and init raises otherwise, as it does when the caller names Newton(). A CuSparseMatrixCSR prototype takes Newton(), which has the cuDSS factor where CUDA and CUDSS are loaded (see Sparse direct solves). The default method is never matrix-free and never a combinator: the problem carries no information that selects either.

R1: one small system as a value

Methods.

methodcondition
Newton with LUFactorizationa square Jacobian
Newton with LDLTFactorizationa symmetric or Hermitian Jacobian; a real Jacobian is read from the lower triangle only, a complex one must be given in full, because both triangles decide between $L D L^\mathsf{T}$ and $L D L^\mathsf{H}$
Newton with CholeskyFactorizationa Hermitian (real symmetric) positive definite Jacobian at every iterate, read from the lower triangle; a Jacobian that is not positive definite gives SINGULAR; in R3 a host Array only, a device array raises an ArgumentError
Newton with QRFactorizationa square Jacobian, or a LeastSquaresProblem
Newton with SVDFactorizationa rank-deficient or nearly singular Jacobian, or a LeastSquaresProblem; the status reports the numerical rank
Newton with regularization = μa singular or nearly singular Jacobian, where the step of $J + \mu I$ is acceptable
QuasiNewton(k), or Newton with reuse = kthe Jacobian and its factorisation dominate the cost of a step; the rate is then linear
Refinement, GMRESRefinementa factorisation precision below the working type, and not a LeastSquaresProblem; in R1 a GMRESRefinement runs the LU-IR passes alone
GaussNewtona LeastSquaresProblem
Picard$I - \omega J$ is a contraction; it needs no Jacobian, and the rate is linear
Anderson, Broydena fixed-point iteration whose map is cheap and whose Jacobian is expensive or unavailable; in R1 the depth is 1 ≤ m ≤ 4
Additive, Multiplicative, Repeat, Switchmembers that run in R1, and a problem that is not a LeastSquaresProblem
Fallbackmembers that run in R1, and a problem that is not a LeastSquaresProblem; each member solves from $x_0$ in turn until one returns SUCCESS

Globalizations. Static applies close to the solution. Backtracking, Bisection and StrongWolfe search along the direction from a distant start. DogLeg and LevenbergMarquardt change the direction and continue where the Jacobian is singular or ill-conditioned; they take no factor reuse (see Globalization).

Conditions of the regime. The static factorisations unroll over the size of the system, so the compile time and the register use grow with it. A GMRES solve and LeftPreconditioned need an array iterate and raise an ArgumentError here. A factorisation precision below the working type saves registers and memory, not operations. solve differentiates through the solve when x₀ or p carries a ForwardDiff.Dual (see Implicit differentiation); a LeastSquaresProblem raises an ArgumentError there.

julia> using GeometricSolvers, StaticArrays

julia> F(x, p) = SVector(x[1]^2 + x[2]^2 - p, x[1] - x[2]);

julia> prob = NonlinearProblem(F);

julia> candidates = (Newton(), Newton(; linsolve = SVDFactorization()), QuasiNewton(3),
                     Newton(; globalization = DogLeg()));

julia> all(candidates) do m
           x, status = solve(prob, SVector(1.0, 0.5), m, 2.0)
           status.code === SUCCESS && x ≈ SVector(1.0, 1.0)
       end
true

R2: many small systems in one launch

Methods. solve_batch! runs the R1 loop in one work-item per system, so a batch takes each method of R1 above, with the same conditions. A LeastSquaresProblem has no batch form. PerSystem and BatchParams give each system its own parameters, and batch_summary reduces the status vector.

Conditions of the regime. The systems are independent and of the same form. On a Vector the kernel runs on the KernelAbstractions CPU() backend. On a GPU backend the problem enters the kernel by value, so each part of it is isbits: a residual that captures a host array, or a sparse jacobian_prototype, cannot enter a device kernel. On Metal the element type is Float32. This page runs no device example.

julia> using GeometricSolvers, StaticArrays

julia> F(x, p) = SVector(x[1]^2 + x[2]^2 - p, x[1] - x[2]);

julia> prob = NonlinearProblem(F);

julia> X = [SVector(1.0, 0.5), SVector(2.0, 1.0), SVector(0.5, 0.1)];

julia> S = Vector{SolverStatus{Float64}}(undef, length(X));

julia> solve_batch!(X, S, prob, Newton(; globalization = Backtracking()), PerSystem([2.0, 8.0, 0.5]));

julia> batch_summary(S).all_converged && X ≈ [SVector(1.0, 1.0), SVector(2.0, 2.0), SVector(0.5, 0.5)]
true

R3: one system in place

Methods. Each method of R1 runs in R3, with no limit on the depth of Anderson and Broyden, and a GMRESRefinement runs its GMRES-IR stage. R3 adds:

methodcondition
LUFactorization on a sparse jacobian_prototypea host Vector iterate of a real element type, Sparspak loaded, the element type of the iterate as the factorisation precision, and a Jacobian from an analytic J! that writes the nonzeros of the prototype or from jacobian = AutoSparse(...) (see Sparse direct solves)
KroneckerFactorizationthe stage system of an implicit Runge–Kutta method, from a NonlinearProblem with stage_matrix and stage_jacobian, whose stage matrix is diagonalisable with cond(V) ≤ max(eps(real(T)), eps(Float64))^(-1/2) and invertible; a host array iterate, Static or a line search, and the step h in p.h
RASlocal nonlinearities that a BlockPartition isolates, and one local residual per block
LeftPreconditionedan inner step N whose fixed points are the wanted roots; each trial point of the outer globalization costs one inner step, and with RAS it needs converged local solves

Refinement converges while the error of the solve in the factorisation precision, roughly the condition number of $J$ times its unit round-off, stays below one, and GMRESRefinement extends that range of condition numbers; where both fail, the step refactorises in the working type. Mixed precision gives the conditions in full.

Conditions of the regime. init allocates each buffer once, so a system that is solved more than once goes through init and solve!. On a device array the factorisation methods run on device kernels. On CUDA, LUFactorization, QRFactorization and SVDFactorization call cuSOLVER for BLAS element types, except an SVDFactorization whose rtol lies below its default cutoff √m · eps(R), with m the row count and R the real type of the factor, which runs on the own kernel; on Metal, LUFactorization calls Metal Performance Shaders for Float32 (see What runs where). The residual of a device solve indexes no scalars. On a device array, LevenbergMarquardt runs with SVDFactorization and scaling = :none only, and the sparse LU does not run. This page runs no device example.

julia> using GeometricSolvers

julia> F!(y, x, p) = (y .= x .^ 2 .- p; y);

julia> method = Newton(; linsolve = LUFactorization(Float32), refinement = Refinement());

julia> solver = init(NonlinearProblem(F!), ones(4), method, [1.0, 4.0, 9.0, 16.0]);

julia> x, status = solve!(solver);

julia> status.code === SUCCESS && x ≈ [1.0, 2.0, 3.0, 4.0]
true

R5: one system without a Jacobian matrix

Methods. Newton with linsolve = GMRES() holds no $n \times n$ Jacobian. Each inner iteration of GMRES takes one Jacobian–vector product, from automatic differentiation or from a JVPFunction.

method or optioncondition
GMRESan AbstractVector iterate, on the host or on a device, and the square system of a NonlinearProblem
EisenstatWalkerChoice2 (the default), EisenstatWalkerChoice1an inner tolerance that is loose far from the root and tight near it
FixedForcing(η)a constant inner tolerance η
a right preconditioner with methods of refresh! and apply_preconditioner!an operator that is refreshed once per Newton step and applied before every product
Static, Backtracking, Bisection, StrongWolfeas in R1
DogLegas in R1; it runs on the Arnoldi relation of one unrestarted cycle without a preconditioner

Conditions of the regime. R5 applies to a large system whose Jacobian no array can hold. A GMRES solve takes no factor reuse, no Refinement, no LevenbergMarquardt and no LeastSquaresProblem, and it has no implicit differentiation; each of them raises an ArgumentError. A Newton with GMRES is not the outer method of a LeftPreconditioned, and raises an ArgumentError there; it can be the inner method. On a device array no factor is formed. f_calls and jvp_calls count the evaluations of the last solve.

julia> using GeometricSolvers

julia> F!(y, x, p) = (y .= x .^ 2 .- p; y);

julia> method = Newton(; linsolve = GMRES(; forcing = FixedForcing(1e-6)));

julia> solver = init(NonlinearProblem(F!), ones(4), method, [1.0, 4.0, 9.0, 16.0]);

julia> x, status = solve!(solver);

julia> status.code === SUCCESS && x ≈ [1.0, 2.0, 3.0, 4.0] && jvp_calls(solver) > 0
true
